- 再試行に成功した場合は正常状態へ自動復帰する。
- API側が再試行待機時間を指定する場合は、その指定を尊重する。
- 認証失効・モデル廃止など、設定変更が必要な恒久的エラーには自動再試行を適用しない。
- 再試行回数・間隔・上限・待機中のItem/Box操作の扱いは詳細設計で決定する。

- 保留処理の保存先・再開順序・待機期限・アプリ再起動時の扱いは未確定とし、順次決定する。

### Vision保留処理の永続化と認識結果確認（2026-11-01確定）

- **A案採用**: 一時的障害中に保留したVision処理をサーバー側に永続保存し、サーバー再起動後も復元可能にする。重複実行を防止する。
- Visionの主目的は、アイテムの説明・タグの入力負担を減らすことである。未入力項目がある場合に画像認識を行う方針とする。説明・タグの片方のみ未入力の場合の細則は未確定。
- 通常フローは「アイテム撮影→画像認識→利用者が結果確認→保管」を想定する。
- Vision障害等で画像認識を保留する場合も、Item・Boxの通常操作や保管を妨げない。復帰後に後追い認識を行う。
- 後追い認識の結果は利用者へ通知し、利用者の確認を必要とする。確認前に説明・タグを自動確定しない。
- 認識処理の完了とアイテム情報への確定反映は分離する。通知方法・承認UI・保留期限・再開順序等は未確定。

### Vision保留処理の永続化とアイテム入力支援（2026-11-01確認）

- **A案採用**: 一時障害中に保留したVision処理はサーバー側に永続保存し、再起動後も復帰・再開できる構成とする。
- Visionの目的はアイテムの説明・タグの入力負担を軽減すること。未入力の場合に画像認識を行う。
- 想定する通常フローは、アイテム撮影時に画像認識し、利用者が認識結果を確認してから保管する方式。
- 一時障害等で後追い認識になった場合は、認識完了後に利用者通知等で認識結果の確認を求める。
- 後追い認識の結果を入力済みの説明・タグに自動反映するか、確認待ち候補として保持するかは未確定（確認待ち候補方式を提案中）。
- 保留処理の再開順序・期限・保存データの範囲・通知方法は今後決定する。

### Vision後追い認識結果の自動反映と通知（2026-11-01確定）

- **B案採用**: 後追い認識が完了した場合、説明・タグの未入力項目へ認識結果を自動反映する。利用者の事前承認は不要。
- 自動反映後に利用者へ認識完了を通知する。
- 利用者は通知から対象アイテムの編集画面へ移動し、説明・タグを修正または再認識できる。
- 既に利用者が入力した説明・タグを後追い認識によって自動上書きしない。
- 説明とタグの未入力判定は別々に扱う。既存タグが一部ある場合の詳細な判定・反映方式は未確定。
- 先行する『後追い認識結果の確認を求める』という記述は、承認待ちではなく自動反映後の通知・任意確認を意味するものとして本決定を優先する。

### Vision後追い認識時の既存タグへの追加（2026-11-01確定）

- **B案採用**: 後追い認識では既存タグを維持し、認識した新しいタグを重複なく追加する。
- 既存タグの削除・変更は行わない。
- 説明文は未入力の場合に限り自動反映し、入力済みの説明文は上書きしない。
- 自動反映後に利用者へ通知し、通知からアイテム編集・再認識を行えるようにする。
- タグの重複判定方法（表記揺れ・大文字小文字など）は詳細設計で確定する。
- 先行する『タグは未入力の場合のみ自動反映』という記述は、本決定により上書きする。

### Visionタグ重複判定の正規化（2026-11-01確定）

- **A案採用**: Visionによるタグ追加時は、比較用文字列を正規化して重複を判定する。
- 前後の空白、全角・半角、大文字・小文字などの表記差を正規化対象とする。具体的なUnicode正規化方式と適用範囲は詳細設計で定義する。
- 正規化後に一致するタグは追加しない。既存タグの表示名・保存値は変更しない。
- 正規化は重複判定にのみ使用し、利用者が設定した元のタグ表記を維持する。
- 意味が似ているだけのタグを自動的に同一視することは本要件に含めない。

### Vision保留処理のFIFO再開順序（2026-11-01確定）

- **A案採用**: Visionの保留処理は受付順（FIFO）で再開する。
- 受付順序をサーバー側で永続管理し、サーバー再起動後も維持する。
- 同時刻の受付などで順序が曖昧にならないよう、順序を一意に定める識別子を用いる（具体方式は詳細設計）。
- 一時的なエラーで再試行する場合も原則として受付順序を維持し、同一アイテムの重複実行を防ぐ。
- 先頭処理が繰り返し失敗した場合の後続処理の扱いは未確定。

### Vision保留キューの厳密FIFOと通常撮影の優先（2026-11-01確定）

- **B案採用**: 保留キューの先頭処理が繰り返し失敗した場合も先頭を維持し、成功するまで後続の保留処理は進めない（厳密FIFO）。
- 保留キューに入るのは、**アイテム撮影時に画像認識エラーとなった処理のみ**。通常の撮影時認識は即時実行し、最初から保留キューに積まない。
- 保留キューの再認識中でも新しいアイテム撮影時の画像認識を優先し、再認識処理へ割り込める構成とする。
- FIFOは保留キュー内の順序にのみ適用し、通常撮影時の認識には適用しない。
- 割り込みは通常撮影の優先を意味する。進行中の外部APIリクエストの強制中断有無、同時実行制御、先頭処理が恒久エラーになった場合の扱いは詳細設計で検討する。
- 先行する『失敗時に後続処理を進める』案は不採用とする。

### Vision通常撮影割り込み時の並行実行（2026-11-01確定）

- **A案採用**: 保留キューの再認識APIリクエストが実行中でも中断せず、新規アイテム撮影の画像認識を別リクエストで優先実行する。
- 保留キュー内の厳密FIFOは維持し、先頭の再認識が成功するまで後続の保留処理を開始しない。
- 保留キューの次の処理を開始する際は、通常撮影の認識処理を優先する。
- 同一アイテムへの重複反映を防止する。
- プロバイダーAPIの同時実行数・レート制限を考慮したスケジューリング、通常撮影と再認識の競合制御は詳細設計で定義する。

### Vision通常撮影割り込みの並行実行（2026-11-01確定）

- **A案採用**: 実行中の保留キュー再認識APIリクエストを中断せず、新規撮影時の画像認識を別リクエストで優先実行する。
- 保留キュー内は厳密FIFOを維持し、次の再認識処理開始時には通常撮影の認識を優先する。
- 同一アイテムへの重複反映を防止する。API同時実行数・レート制限制御は詳細設計で定める。

### Vision保留キューの無期限保持（2026-11-01確定）

- **A案採用**: 保留キューの処理には待機期限を設けず、認識成功まで永続保持する。
- 一時的な障害の長期化やサーバー再起動を理由に保留処理を自動削除しない。
- 保留キューの厳密FIFOを維持する。
- 認証失効・モデル廃止など自動再試行で回復できないエラーは無制限にAPI呼び出しせず停止状態で保持する。停止からの復帰条件は未確定。

### Vision恒久的エラー停止からの自動復帰（2026-11-01確定）

- **A案採用**: APIキー無効・認証失効・モデル廃止などの恒久的エラーでVisionが停止した場合、保留キューを削除せず保持する。
- Settings > VisionでAPIキーまたはモデルなどの設定を変更した際、自動的に実API検証を行う。
- 検証成功時はVisionを正常状態に復帰させ、保留キューを厳密FIFO順に自動再開する。手動テストボタンの実行を復帰条件にしない。
- 検証失敗時は停止状態を維持し、設定内容とエラー情報を保持する。

- **A案採用**：通知データの正本はサーバーDBで管理する。
- 複数端末はAPIを介して同じ通知データを参照し、確認状態変更・削除の結果はサーバーを通じて共有する。
- オフライン時は通知の状態変更・削除を行わない。既存Businessデータの同期モデルには通知を含めない。
- 通知一覧の表示件数・並び順・絞り込み条件は、既定どおり端末ごとにローカル保存し、端末間同期しない。
- 通知のDBフィールド、識別子、参照整合性などはデータモデル詳細設計で別途定義する。


### 通知の識別子とユーザー境界（2026-11-09確定）

- **B案採用**：通知の識別単位を `(userId, id)` とし、DBの複合主キーとする。
- `userId` は通知の所有者であり、`User.id` を参照する。`id` は同一ユーザー内で一意とし、異なるユーザー間で同じ値を許可する。
- APIの通知操作は認証結果の `userId` と通知 `id` の組合せで対象を特定する。リクエスト中の `userId` を認可根拠にしない。
- 通知データのサーバー管理方式は維持し、Business同期モデルへは含めない。
- 通知IDの生成主体・形式は別途決定する。


### 通知ID採番方式（2026-11-09確定）

- 通知IDはサーバーでUUID v4を生成する。DBの識別単位・複合主キーは `(userId, id)` を維持する。
- UUIDの衝突可能性を考慮し、DBの複合主キー制約で一意性を保証する。事前存在確認だけに依存しない。
- 通知INSERT時、通知の複合主キー衝突と識別できる場合に限り、新しいUUID v4を生成して再試行する。その他の制約違反は再採番対象としない。
- 初回INSERTと再試行を合わせて最大3回とし、上限到達時は通知作成失敗としてログに記録する。
- UUID方式ではユーザー別連番カウンターの排他採番は設けない。


### 通知の確認状態保存方式（2026-11-10確定）

- **A案採用**：通知の確認状態は `readAt` のみで永続化し、`isRead` 等の別状態列は設けない。
- `readAt = NULL` は未確認、`readAt != NULL` は確認済みを表す。
- 未確認への変更は `readAt = NULL` とし、確認済みへの変更は未確認の場合に限りサーバーの確認日時を設定する。
- 確認済み通知の再表示・再確認では `readAt` を変更しない。
- 保存期限は `readAt + 720時間` で判定する。未確認通知は期限なし。期限切れ通知は状態変更不可。


### 通知の保存期限算出方式（2026-11-11確定）

- **A案採用**：通知の削除期限を表す `expiresAt` 等の永続DB列は設けない。
- 有効期限はサーバーが `readAt + 720時間` で算出する。`readAt = NULL`（未確認）の通知は期限なし。
- `readAt` が非NULLで現在時刻が `readAt + 720時間` 以上なら期限切れとする。作成日時は起算点にしない。
- 期限判定は一覧・件数・詳細・状態変更・手動削除・定期削除で一貫して適用する。物理削除が遅れても期限切れを有効として扱わない。
- 期限内に未確認へ戻した場合は `readAt = NULL` により期限が解除される。


### 通知日時の保存精度（2026-11-11確定）

- **A案採用**：通知の `createdAt` と `readAt` は、既存サーバーDB仕様と同じUTCミリ秒精度で保存する。
- 日時の比較および `readAt + 720時間` の期限判定もUTCミリ秒単位で行う。
- `readAt = NULL` は未確認を表す。DBでの具体的な日時型は別途詳細設計で定義する。

## 2. 正式登録フロー

標準登録順序は次のとおり。

1. 箱登録
2. アイテム
3. 箱写真
4. ラベル
5. 場所

場所はスキップ可能な後決め項目とする。新規Boxの `locationId` は原則 `UNASSIGNED` とし、箱詰め後・引っ越し後などに置き場所を確定できる。

根拠:
- 引っ越しでは置き場所を決めずに箱詰めを進め、移動後に未開封箱の保管場所を決める運用が自然なため。
- 現行 `RegisterClient.tsx` の登録順序とも整合するため。

## 3. アイテムの取り出しと削除

### 3.1 取り出す
- 「箱から取り出した」を表す。
- アイテム自体は削除しない。
- `boxId = UNASSIGNED` に変更する。
- 名前、タグ、メモ、写真等は保持する。

### 3.2 削除する
- 「アイテムを捨てた」を表す。
- `deletedAt` を設定して論理削除する。
- 同期による削除受理後、ローカルtombstoneを物理削除できる。

UIでは「取り出す」と「削除する」を明確に区別する。

## 4. Box / UNASSIGNED

各ユーザーは予約Box `UNASSIGNED` を持つ。

- `id = UNASSIGNED`
- `code = UNASSIGNED`
- Itemがどの箱にも入っていない状態を `Item.boxId = UNASSIGNED` で表す。
- 予約Boxは通常削除不可・通常編集不可。

箱削除時:
- 所属Itemを `UNASSIGNED` へ移動する。
- Box自体は `deletedAt` を設定して論理削除する。
- BoxLocationは独立した置き場所マスタなので削除しない。

## 5. BoxLocation

BoxLocationはBox従属1:1ではなく、部屋・押入れ・棚など「置き場所そのもの」を表す独立マスタとする。

### 5.1 関係
- Box : BoxLocation = 多対1
- BoxLocationへ直接置かれたtop-level Boxだけが `locationId` でBoxLocationを参照する。
- Boxはoptional `parentBoxId` で同一Userの別Boxを収納先として指定できる。
- parentBoxIdはself/descendantを指定不可としcycleを禁止する。
- nested Boxは `locationId=null` とし、収納先を `parentBoxId` だけで表現する。物理場所はancestor Box chainを辿って最上位BoxのlocationIdから解決する。
- parent Box削除時はdirect child Boxだけを箱から出し `parentBoxId=null`, `locationId=UNASSIGNED` とする。さらに下のBox nestingは維持する。
- BoxLocationに `boxId` は持たせない。
- BoxLocation master自体は階層構造を持たせない。Boxの入れ子はBox.parentBoxIdで表現する。

### 5.2 予約置き場所
各ユーザーは予約BoxLocation `UNASSIGNED` を持つ。

- 新規Boxの `locationId = UNASSIGNED`
- 「置き場所未定」を通常状態として扱う。
- `UNASSIGNED` BoxLocationは通常削除不可・通常編集不可。

### 5.3 項目案

```text
id
name
note
thumbs
meta
aiState
aiUpdatedAt
createdAt
updatedAt
deletedAt
serverUpdatedAt
revision
contentHash
syncSeq
```

`code` は持たせない。

### 5.4 name一意・後勝ち
- `BoxLocation.name` は同一ユーザー内で一意。
- 同名が発生した場合、新しくサーバーが受理する名称を優先する「後勝ち」とする。
- 既存側を `名前(n)` へ自動改名する。
- `n` は未使用の最小正整数。
- 「後」は端末 `updatedAt` ではなくサーバー受理順で決める。
- 異なるID同士の同名はrevision競合ではなく名前一意制約の自動解決として扱う。
- 既存側の自動改名も通常の業務更新として `updatedAt` / `contentHash` / `revision` / `serverUpdatedAt` / `syncSeq` / `SyncChangeLog` を更新する。
- 新規/変更対象の保存と既存側の自動改名は同一サーバートランザクション。
- `UNASSIGNED` は予約名のため通常レコードへの使用禁止。

例:

```text
既存: 書斎
新規: 書斎

結果:
既存: 書斎(1)
新規: 書斎
```

### 5.5 BoxLocation削除
通常BoxLocation削除時:
1. 参照しているBoxの `locationId` を `UNASSIGNED` へ変更。
2. 各Boxの同期メタデータを更新。
3. BoxLocationをtombstone化。
4. 対応するSyncChangeLogを追加。

一つの論理操作として原子的に実行する。

## 6. 写真保存方式

正式フィールドは `thumbs` とする。

現行 `backup.ts` の `photoThumbs` は不整合であり実装修正対象。

## 7. 同期メタデータ

Box / Item / BoxLocation に以下を持たせる。

```text
createdAt
updatedAt
deletedAt
serverUpdatedAt
revision
contentHash
syncSeq
```

意味:
- `createdAt`: データ作成時刻
- `updatedAt`: 実データ内容の最終変更時刻
- `deletedAt`: 論理削除時刻。通常状態はnull
- `serverUpdatedAt`: サーバーが最後に受理・更新した時刻
- `revision`: サーバー管理のレコード版番号
- `contentHash`: 内容同一性判定
- `syncSeq`: サーバー変更通番

新規ローカルレコードは `revision = 0`、初回サーバー登録成功時に `revision = 1` とする。

## 8. 同期競合方式

`updatedAt` の新旧では勝敗を決めない。

Push時:

```text
baseRevision == server.revision
→ 通常更新

baseRevision != server.revision
→ contentHash比較
   同一     → 実質同一内容として競合不要
   不一致   → ユーザー確認が必要な競合
```

`updatedAt` は表示・監査・補助情報として保持するが、自動競合解決の勝者判定には使わない。

## 9. contentHash

同期とバックアップの衝突判定で同じcanonical化・hash計算仕様を共通利用する。

含める:
- 業務内容
- 削除状態（active / deleted）

除外:
- `id`
- `userId`
- `createdAt`
- `updatedAt`
- `deletedAt` の時刻値
- `serverUpdatedAt`
- `revision`
- `syncSeq`
- `contentHash`

正規化:
- object key順を決定的にする。
- 順序非依存配列（例: tags）はソートする。
- canonical JSON化後、SHA-256等の決定的hashを使用する。

## 10. 削除伝播

論理削除フィールドは `deletedAt` に統一する。

サーバーtombstone保持期間は30日。

ローカル:
1. 削除操作
2. `deletedAt` 設定
3. Outboxへ記録
4. Push
5. サーバーが削除を受理
6. 受理結果を確認後、ローカルtombstoneを物理削除

オフライン中はPush成功までローカルtombstoneを保持する。

## 11. Outbox

未同期変更はOutboxで明示管理する。

- 業務更新とOutbox更新は同一ローカルトランザクション。
- Push対象は `updatedAt > lastPushAt` ではなくOutbox。
- 同一エンティティの未同期変更は原則1件へ集約し、最新状態を保持。
- 集約しても最初の編集元 `baseRevision` を維持。
- Push成功または競合解決成功まで保持。
- 時間による自動削除なし。
- full resyncでもOutboxを保持し、サーバー正本再構築後に再適用する。

候補項目:

```text
id
entityType
entityId
operation
baseRevision
contentHash
payload
createdAt
```

## 12. SyncChangeLog / syncSeq

- `SyncChangeLog` を同期変更履歴の正本とする。
- Box / Item / BoxLocationにも最新の `syncSeq` を保持する。
- レコード更新とSyncChangeLog追加は同一トランザクション。
- `syncSeq` はDB全体で一意・単調増加する64bit符号付き整数。
- Pullは認証済み `userId` で絞り、`syncSeq > cursor` を返す。
- SyncChangeLog保持期間は90日。
- 対象ユーザーについてcursorが保持範囲より古い場合は `FULL_RESYNC_REQUIRED`。
- full resync時はOutboxを保持・再適用する。
- `syncEpoch` は採用しない。

## 13. SyncConflict

SyncConflictは監査履歴ではなく、未解決競合の一時保持領域とする。

候補項目:

```text
id
userId
entityType
entityId
clientBaseRevision
clientContentHash
clientPayload
serverRevisionAtConflict
serverContentHashAtConflict
serverPayloadAtConflict
createdAt
```

同じPushの再送で同じ競合を重複作成しない。
候補一意キー:
`(userId, entityType, entityId, clientBaseRevision, clientContentHash)`

### 13.1 stale SyncConflict

競合解決時に、現在の `server.revision` と `serverRevisionAtConflict` を必ず再比較する。

一致:
- 保存済み競合をそのまま解決可能。

不一致:
- 競合発生後に正本が更新された stale 状態。
- 新しいSyncConflict行は増やさない。
- 既存SyncConflictのserver snapshotを最新正本へ更新する。
- 最新 `contentHash` とclient側を再比較する。

再比較結果:
- 同一 → 実質的に競合解消済みとしてSyncConflict削除、Outboxも成功扱いで削除。
- 不一致 → 最新のclient版 / server版をユーザーへ再提示する。

競合解決時の正本更新、revision更新、serverUpdatedAt更新、syncSeq採番、SyncChangeLog追加、SyncConflict削除は同一トランザクションで行う。

根拠:
- 古いserver snapshotを基準に上書きすると、その後の更新を失う可能性があるため。
- SyncConflictは履歴ではなく未解決状態の保持が目的なので、staleになるたび行を増やす必要がないため。

## 14. トランザクション境界

Pushバッチ全体は巨大トランザクションにしない。
整合性が必要な「論理操作単位」で原子的に処理する。

通常更新:
1. revision確認
2. contentHash比較
3. 正本更新
4. revision更新
5. serverUpdatedAt更新
6. syncSeq採番
7. SyncChangeLog追加
8. commit

Box削除、BoxLocation削除、BoxLocation名後勝ち自動改名など、複数レコードの整合性を伴う操作はそれぞれ一つの論理トランザクションにする。

## 15. ユーザー分離 / 所有権

サーバーは複数ユーザーを保持し、同一ユーザーの複数端末が同一データ集合を同期する。

Box / Item / BoxLocation のサーバー上識別単位:

```text
(userId, id)
```

異なるユーザーは同一 `id` を持ってよい。
Pushの `userId` はpayloadを信用せず認証結果から確定する。

Item→Box、Box→BoxLocationなどの参照も同一userId内に限定する。

## 16. バックアップID / ハッシュ

バックアップは元のBusiness identityと同期用と同じcanonicalizationによる `contentHash` を保持する。

Restore:
- backupは作成したUserと同一UserへのRestoreのみ許可する。
- identity不存在 → validation後、元identityのままauto-add candidate。
- 同一identity + 同一business content → UNCHANGED。
- 同一identity + 異なるbusiness content → `KEEP_EXISTING / USE_BACKUP` を利用者が選択する。
- Restoreを理由とする一般的なentity ID再採番は行わない。
- backup由来のsync metadataは導入しない。
- `userId` はcontentHashに含めないが、これはcross-user Restoreを許可する意味ではない。

Boxは追加のintegrity ruleを持つ。
- Box.codeはimmutable。
- same Box.id + different codeはreject。
- different Box.id + duplicate codeはreject。
- noncanonical Box.codeはreject。

詳細正本は `docs/ja-JP/02_アーキテクチャ/90_Backup_Restore設計.md` と `70_BoxCode_Device設計.md` を参照する。

3. 現行Pushはrevision/contentHash競合に未対応。
4. 現行Pullはtimestamp `since` ベース。

7. backup対象にBoxLocationがない。

9. 現行Box削除はローカル物理削除。
10. 現行PrismaのBox / Item / BoxLocationの `id` は全ユーザー共通主キー。
11. 現行Pushは `where: { id }` でupsertし、update時にuserIdも書き換えるため所有権侵害リスクがある。
12. 現行BoxLocationは `boxId` を持つBox従属モデルで、確定要件と逆方向。
