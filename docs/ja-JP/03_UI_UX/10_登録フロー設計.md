# 登録フロー設計

## 1. Scope
v0.8標準登録フロー:
`Box -> Items -> Box photo -> Label -> Location -> Complete`

wizard全体を1 transactionとして扱わない。各Business変更は通常local Business + Outbox規則で即時保存する。

## 2. Box step
Box stepでrequired fieldを満たし「次へ」を実行した時点でBoxを作成する。

同一IndexedDB transaction:
- Box create
- Outbox UPSERT
- Box.code LocalSequence increment

成功後のみItems stepへ進む。Box作成transaction失敗時はstepを進めず、code sequenceもcommitしない。

## 3. Items step
Itemは1件ごとに通常create/updateとして保存する。
- Item追加成功後、一覧へ即反映
- 複数Itemをwizard終了まで未保存状態にしない
- 0件でも次へ進める
- stepを戻っても作成済みItemを削除しない
Item削除は通常delete/tombstone規則。

## 4. Box photo step
写真は1枚ごとにPhoto / Blob設計のnormal ingestionで保存する。
- 0枚でもskip/next可能
- 追加済み写真は戻る/cancelで自動削除しない
- 写真削除は通常photo delete + Undo

## 5. Label step
LabelはBusiness save stepではない。preview / print/export / skipのいずれもBox Businessを変更しない。print/export失敗でも登録済みBoxをrollbackしない。

## 6. Location step
Locationはoptional step。初期Boxは `locationId=UNASSIGNED` で成立する。Location選択/作成後の割当は通常Box updateとして保存する。
- skip -> UNASSIGNEDのままComplete
- existing Location選択 -> Box update
- new Location作成 -> BoxLocation create後、Box.locationId update
- save失敗 -> Complete扱いにせずretry/skip可能

## 7. Back
「戻る」はnavigation。
- previous stepへ移動
- 保存済みBusinessをrollbackしない
- previous stepのcurrent canonical local stateを表示
- 修正した場合は新しい通常Business update

PhotoからItemsへ戻っても既存photoは保持される。Item編集は通常update。

## 8. Skip
skip可能:
- Items: 0件で次へ
- Box photo: 0枚で次へ
- Label: 印刷せず次へ
- Location: UNASSIGNEDで完了

Box stepはskip不可。既にdataがあるstepでskipしても既存dataを削除せず、追加操作せず次へ進むだけ。

## 9. Cancel
Box作成前: draft破棄、Business/Outbox変更なし、Device sequence変更なし。

Box作成後:
- 「登録フローを終了」として扱う
- 作成済みBox/Item/photo等を保持
- Boxを自動deleteしない
- pending Outboxも保持
- 通常Box detail/listへ戻る

作成済みBoxを消す場合は別の明示的Box delete操作を使用する。

## 10. Close / reload / crash
Box作成前の未commit form draftはv0.8で永続化保証しない。Box作成後は各stepが即時保存なのでreload/crash後もBusinessは保持される。wizardの現在stepをBusiness correctness上の必須persistent stateにしない。再開時はBox detailから必要操作を継続できる。

## 11. Offline
healthy DeviceStateにcode発行余地があれば全registration Business stepをoffline実行可能。Device prefix exhaustedでonline allocation不能の場合はBox stepで新規Box作成のみblockする。

## 12. Sync
wizard完了をPush条件にしない。保存されたBusiness/Outboxは通常Sync対象。wizard途中でもnetwork条件が整えばSync可能。SyncConflictでもwizard全体をrollbackしない。

## 13. Complete
Location stepのnextまたはskipでComplete。Completeは新しいBusiness transactionではなくUI state。完了後はBox detailへ遷移しlocal sync stateを表示可能。`完了済み` Business flagは追加しない。

## 14. Destructive confirmation
Back/Skip/Cancelではdestructive confirmation不要。保存済みBusinessを削除しないため。明示delete/photo delete等だけ通常delete UI規則に従う。

## 15. Sync state display

### 15.1 Global state
Global sync indicatorは次の優先状態を表示する。

- `RESTORE_LOCKED`: Restore中。通常server Sync停止
- `AUTH_EXPIRED`: 再認証待ち
- `OFFLINE`: network unavailable
- `CONFLICT`: unresolved SyncConflictあり
- `BLOCKED`: permanent/local-action-required dependencyあり
- `SYNCING`: Pull/Push/blob preparation等を実行中
- `PENDING`: Outboxまたは未CONFIRMED required photoあり
- `SYNCED`: 上記なし、normal Syncが完了可能な状態

複数条件が同時成立する場合、よりactionableな状態を優先表示する。詳細画面では併存条件を個別表示可能。

### 15.2 Entity state
Box / Item / BoxLocation detail/listでは必要に応じてentity単位状態を表示する。

- `SYNCED`: current local Businessに対応するpending Outbox/conflict/blockなし
- `PENDING`: entity Outboxあり
- `SYNCING`: current sync cycleで処理中
- `CONFLICT`: entityのunresolved SyncConflictあり
- `BLOCKED`: photo/reference/validation等でPush不可

`OFFLINE` / `AUTH_EXPIRED` / `RESTORE_LOCKED` はentity content状態ではなくglobal transport/session状態として併記する。

### 15.3 Photo dependency
Business Outboxがあり、required photoがserver-readyでない場合は単なる通信中とせず状態を区別する。

- retryable upload待ち -> PENDING
- upload処理中 -> SYNCING
- missing original/permanent validation failure -> BLOCKED

BLOCKEDではreasonを表示し、他entityのSyncまで失敗したように見せない。

### 15.4 Conflict
CONFLICTは通常の未同期より強く表示する。

- conflictがあってもlocal editingは可能
- latest local Business/Outboxを「この端末」候補として表示
- 解決後は通常Sync stateへ戻る
- stale resolution時は再比較を要求

### 15.5 Last sync time
`lastPullAt` / `lastPushAt` は補助情報でありstate判定の正本にしない。

表示例:
- 最終受信: 10分前
- 最終送信: 3分前

時刻が新しくてもOutboxがあればSYNCED表示にしない。

### 15.6 Pending count
Global UIは必要に応じて次をcount表示できる。
- pending Outbox entities
- conflicts
- blocked entities

photo upload file数をBusiness pending件数と混同しない。

### 15.7 Manual sync
利用者はonline/authenticated/Restore unlocked時に「同期」操作を実行可能。

manual syncも通常Sync sequenceを使用し、別のmerge semanticsを持たない。

連打で同一Userのnormal Syncを並列実行せず、既存cycleへjoinまたは次cycle要求としてcoalesceする。

### 15.8 Completion feedback
normal Sync cycle成功時:
- pending/conflict/blockが0なら `同期済み`
- pendingが残るなら `未同期あり`
- conflictが残るなら `競合あり`
- blockedが残るなら `確認が必要`

HTTP requestが成功しただけで全体を「同期済み」と表示しない。

### 15.9 UI placement
最低限:
- app-level header/status area: global state
- Box/Item/Location list/detail: non-SYNCED entity badge
- conflict screen: conflict count/detail

SYNCED entity badgeは一覧で常時表示せず簡略化してよい。異常/pending状態を優先する。

### 15.10 Accessibility
stateは色だけで区別しない。text/icon/accessible labelを併用する。

animationだけでSYNCINGを表現しない。

## 16. Design complete
登録フローのnavigation/save boundaryは確定。
