# 登録フロー設計

## 1. Scope
v0.8標準登録フロー:
`Box -> Items -> Box photo -> Label -> Location -> Complete`

wizard全体を1 transactionとして扱わない。各Business変更は通常local Business + Outbox規則で即時保存する。

## 2. Box step
Box stepでrequired fieldを満たし「次へ」を実行した時点でBoxを作成する。

同一IndexedDB transaction:
- Box create
- Outbox UPSERT
- Box.code LocalSequence increment

成功後のみItems stepへ進む。Box作成transaction失敗時はstepを進めず、code sequenceもcommitしない。

## 3. Items step
Itemは1件ごとに通常create/updateとして保存する。
- Item追加成功後、一覧へ即反映
- 複数Itemをwizard終了まで未保存状態にしない
- 0件でも次へ進める
- stepを戻っても作成済みItemを削除しない
Item削除は通常delete/tombstone規則。

## 4. Box photo step
写真は1枚ごとにPhoto / Blob設計のnormal ingestionで保存する。
- 0枚でもskip/next可能
- 追加済み写真は戻る/cancelで自動削除しない
- 写真削除は通常photo delete + Undo

## 5. Label step
LabelはBusiness save stepではない。preview / print/export / skipのいずれもBox Businessを変更しない。print/export失敗でも登録済みBoxをrollbackしない。

## 6. Location step
Locationはoptional step。初期Boxは `locationId=UNASSIGNED` で成立する。Location選択/作成後の割当は通常Box updateとして保存する。
- skip -> UNASSIGNEDのままComplete
- existing Location選択 -> Box update
- new Location作成 -> BoxLocation create後、Box.locationId update
- save失敗 -> Complete扱いにせずretry/skip可能

## 7. Back
「戻る」はnavigation。
- previous stepへ移動
- 保存済みBusinessをrollbackしない
- previous stepのcurrent canonical local stateを表示
- 修正した場合は新しい通常Business update

PhotoからItemsへ戻っても既存photoは保持される。Item編集は通常update。

## 8. Skip
skip可能:
- Items: 0件で次へ
- Box photo: 0枚で次へ
- Label: 印刷せず次へ
- Location: UNASSIGNEDで完了

Box stepはskip不可。既にdataがあるstepでskipしても既存dataを削除せず、追加操作せず次へ進むだけ。

## 9. Cancel
Box作成前: draft破棄、Business/Outbox変更なし、Device sequence変更なし。

Box作成後:
- 「登録フローを終了」として扱う
- 作成済みBox/Item/photo等を保持
- Boxを自動deleteしない
- pending Outboxも保持
- 通常Box detail/listへ戻る

作成済みBoxを消す場合は別の明示的Box delete操作を使用する。

## 10. Close / reload / crash
Box作成前の未commit form draftはv0.8で永続化保証しない。Box作成後は各stepが即時保存なのでreload/crash後もBusinessは保持される。wizardの現在stepをBusiness correctness上の必須persistent stateにしない。再開時はBox detailから必要操作を継続できる。

## 11. Offline
healthy DeviceStateにcode発行余地があれば全registration Business stepをoffline実行可能。Device prefix exhaustedでonline allocation不能の場合はBox stepで新規Box作成のみblockする。

## 12. Sync
wizard完了をPush条件にしない。保存されたBusiness/Outboxは通常Sync対象。wizard途中でもnetwork条件が整えばSync可能。SyncConflictでもwizard全体をrollbackしない。

## 13. Complete
Location stepのnextまたはskipでComplete。Completeは新しいBusiness transactionではなくUI state。完了後はBox detailへ遷移しlocal sync stateを表示可能。`完了済み` Business flagは追加しない。

## 14. Destructive confirmation
Back/Skip/Cancelではdestructive confirmation不要。保存済みBusinessを削除しないため。明示delete/photo delete等だけ通常delete UI規則に従う。

## 15. Sync state display

### 15.1 Global state
Global sync indicatorは次の優先状態を表示する。

- `RESTORE_LOCKED`: Restore中。通常server Sync停止
- `AUTH_EXPIRED`: 再認証待ち
- `OFFLINE`: network unavailable
- `CONFLICT`: unresolved SyncConflictあり
- `BLOCKED`: permanent/local-action-required dependencyあり
- `SYNCING`: Pull/Push/blob preparation等を実行中
- `PENDING`: Outboxまたは未CONFIRMED required photoあり
- `SYNCED`: 上記なし、normal Syncが完了可能な状態

複数条件が同時成立する場合、よりactionableな状態を優先表示する。詳細画面では併存条件を個別表示可能。

### 15.2 Entity state
Box / Item / BoxLocation detail/listでは必要に応じてentity単位状態を表示する。

- `SYNCED`: current local Businessに対応するpending Outbox/conflict/blockなし
- `PENDING`: entity Outboxあり
- `SYNCING`: current sync cycleで処理中
- `CONFLICT`: entityのunresolved SyncConflictあり
- `BLOCKED`: photo/reference/validation等でPush不可

`OFFLINE` / `AUTH_EXPIRED` / `RESTORE_LOCKED` はentity content状態ではなくglobal transport/session状態として併記する。

### 15.3 Photo dependency
Business Outboxがあり、required photoがserver-readyでない場合は単なる通信中とせず状態を区別する。

- retryable upload待ち -> PENDING
- upload処理中 -> SYNCING
- missing original/permanent validation failure -> BLOCKED

BLOCKEDではreasonを表示し、他entityのSyncまで失敗したように見せない。

### 15.4 Conflict
CONFLICTは通常の未同期より強く表示する。

- conflictがあってもlocal editingは可能
- latest local Business/Outboxを「この端末」候補として表示
- 解決後は通常Sync stateへ戻る
- stale resolution時は再比較を要求

### 15.5 Last sync time
`lastPullAt` / `lastPushAt` は補助情報でありstate判定の正本にしない。

表示例:
- 最終受信: 10分前
- 最終送信: 3分前

時刻が新しくてもOutboxがあればSYNCED表示にしない。

### 15.6 Pending count
Global UIは必要に応じて次をcount表示できる。
- pending Outbox entities
- conflicts
- blocked entities

photo upload file数をBusiness pending件数と混同しない。

### 15.7 Manual sync
利用者はonline/authenticated/Restore unlocked時に「同期」操作を実行可能。

manual syncも通常Sync sequenceを使用し、別のmerge semanticsを持たない。

連打で同一Userのnormal Syncを並列実行せず、既存cycleへjoinまたは次cycle要求としてcoalesceする。

### 15.8 Completion feedback
normal Sync cycle成功時:
- pending/conflict/blockが0なら `同期済み`
- pendingが残るなら `未同期あり`
- conflictが残るなら `競合あり`
- blockedが残るなら `確認が必要`

HTTP requestが成功しただけで全体を「同期済み」と表示しない。

### 15.9 UI placement
最低限:
- app-level header/status area: global state
- Box/Item/Location list/detail: non-SYNCED entity badge
- conflict screen: conflict count/detail

SYNCED entity badgeは一覧で常時表示せず簡略化してよい。異常/pending状態を優先する。

### 15.10 Accessibility
stateは色だけで区別しない。text/icon/accessible labelを併用する。

animationだけでSYNCINGを表現しない。

## 16. Offline / authentication / Restore state UI

### 16.1 Common rule
状態表示は最低限、次を利用者へ伝える。

- 現在の状態
- 何が継続可能か
- 何が保留/停止しているか
- 必要なら次のaction

単なる「エラー」表示にしない。

### 16.2 OFFLINE
network unavailable時はapp-levelにOFFLINEを表示する。

表示concept:
- 「オフライン」
- 「この端末への変更は保存され、オンライン復帰後に同期されます」

許可:
- local Business閲覧/編集
- Outbox commit
- local photo操作
- search
- local QR lookup
- label preview/export
- healthy DeviceStateでのBox作成

server確認が必要な操作では個別に「オンライン接続が必要」を表示する。

既存local data全体をdisabledにしない。

### 16.3 AUTH_EXPIRED
server authenticationが期限切れならapp-levelにAUTH_EXPIREDを表示する。

表示concept:
- 「再認証が必要です」
- 「この端末への変更は保持されています」
- primary action: 「再認証」

local session bindingが有効な間はlocal閲覧/編集を継続可能。

Push/Pull/Restore/server conflict resolve/new Device prefix等は保留。

再認証失敗でもlocal dataを消さない。

### 16.4 RESTORE_LOCKED
current UserにRestore lockが存在しnormal server operationが拒否された場合、RESTORE_LOCKEDを表示する。

自端末がRestore owner:
- Restore progress UIを優先
- normal SyncはRestore完了まで待機
- Restore apply中のcancel可否はRestore設計に従う

他端末/他tab由来:
- 「別の復元処理が進行中です」
- local Businessは保持
- server Syncは待機
- retry可能になれば通常Sync再開

RESTORE_LOCKEDをdata conflictとして表示しない。

### 16.5 Combined states
OFFLINE + pending Outboxなど複数状態は共存可能。

Global primary statusはactionability優先で表示し、詳細では併存状態を表示する。

例:
- OFFLINE + 3件未同期
- AUTH_EXPIRED + 5件未同期
- RESTORE_LOCKED + 2件未同期

pending件数を失敗件数として表現しない。

### 16.6 Operation-level message
server-only actionを利用者が実行した時:
- OFFLINE -> 「オンライン接続後に実行してください」
- AUTH_EXPIRED -> 「再認証後に実行してください」
- RESTORE_LOCKED -> 「復元処理の完了後に実行してください」

可能な場合はaction buttonを併記する。

操作不能理由をdisabled buttonだけで表現しない。

### 16.7 Recovery
network復帰:
- 自動でnormal connectivity stateへ
- auth有効ならnormal Sync可能
- auth expiredならAUTH_EXPIREDへ

再認証成功:
- same User確認後AUTH_EXPIRED解除
- normal Sync

Restore lock解除:
- RESTORE_LOCKED解除
- normal Sync再開可能

state解除時にlocal Businessをreload前状態へrollbackしない。

### 16.8 QR/search implications
offline QR local missではserver未登録と断定せず、既存QR設計の「この端末のデータには見つかりません」を使用する。

offline searchはlocal dataset対象であることを必要に応じて示す。

### 16.9 Persistent vs transient UI
短いnetwork揺らぎごとにblocking modalを出さない。

- global banner/status: persistent condition
- toast: operation result等のtransient feedback
- modal: explicit confirmation/re-authentication等、利用者actionが必要な場合のみ

OFFLINE/RESTORE_LOCKEDを毎回modalで通知しない。

### 16.10 Accessibility
banner/statusはscreen readerから状態変化を認識可能にする。

状態を色だけで区別しない。

primary actionのfocus順序を自然に保ち、状態変化だけでfocusを強制移動しない。

## 17. Delete / Undo UI

### 17.1 Common delete rule
Business entity（Item / Box / BoxLocation）のdeleteは実行前にdestructive confirmationを行う。PhotoRef deleteはPhoto / Blob設計どおり即時Business update + 10秒Undo。

### 17.2 Item delete
確認にはItem名と削除結果を明示する。confirm後はItem tombstone + Outbox DELETE、active一覧から除外しPENDING表示可能。v0.8でItem deleteの汎用10秒Undoは必須にしない。

### 17.3 Box delete
確認にはBox code/name、child Item count、「Itemは削除されずUNASSIGNEDへ移動」を明示する。confirm後は同一canonical transactionでchild ItemsをUNASSIGNEDへ更新してOutbox更新後、Box tombstone + Outbox DELETE。途中状態をUIへ見せない。Box.codeは再利用しない。

### 17.4 BoxLocation delete
確認にはLocation名、affected Box count、「Boxは削除されずlocationId=UNASSIGNEDになる」を明示する。confirm後は参照Boxes更新後、Location tombstone + Outbox DELETE。

### 17.5 Photo delete
delete成功後は写真を即時除外し、「写真を削除しました」+「元に戻す」をtoast/snackbar等で10秒表示する。Syncは10秒待たない。

### 17.6 Photo Undo
Undoは通常Business update。current parent active、same photo未参照、blob条件を満たす場合にPhotoRefを再挿入する。成功時だけ復帰表示。thumbnail欠落は再生成可能。original不足等で復帰不能ならreason/actionを表示し、押下だけで成功扱いしない。

### 17.7 Multiple photo deletes
各deleteに独立10秒window。UI actionはLIFOを基本とし最新deleteからUndo。parent delete時はそのparentのphoto Undoを無効化する。

### 17.8 Offline and pending
offlineでもdelete/Photo Undoはlocal-first。Business local stateを即時反映しOutbox PENDING。OFFLINEと併記可能。deleteを単なる予約扱いにしない。

### 17.9 Conflict
delete後のremote change conflictは自動rollbackせず、通常Conflict UIでactive/deleted stateを比較しKEEP_SERVER / USE_LOCALを選択する。

### 17.10 Confirmation design
対象名と結果を具体的に書く。「本当によろしいですか？」だけは禁止。Box/Locationではchild dataへの影響を明示する。confirm buttonは「削除」、cancelは「キャンセル」。

### 17.11 Accessibility / touch
deleteと通常navigationを隣接させすぎない。mobile touch targetを確保しicon-onlyにもaccessible nameを付ける。Undoはscreen reader操作可能にし、残り時間を色だけで示さない。10秒終了時にfocusを強制移動しない。

## 18. Accessibility / Mobile / PWA baseline

### 18.1 Scope
v0.8ではdesktop browser / mobile browser / installed PWAで同じBusiness semanticsを提供する。layoutや利用可能なdevice capabilityは異なってよいが、保存・Sync・Delete・Conflict等の意味を変えない。

### 18.2 Responsive layout
主要画面は狭いmobile viewportでもhorizontal scrollを前提にしない。例外はBusiness上必要なwide data表示で、代替表示を優先する。

navigation、form、dialog、status、registration flowはportrait mobileを基本確認対象にする。

viewport resize/orientation changeで未commit inputを意図せず破棄しない。

### 18.3 Touch
主要interactive controlは誤操作を避ける十分なtouch targetと間隔を確保する。

hoverのみで必要情報や操作を提供しない。drag gestureだけを唯一の操作方法にしない。

camera/QR、photo、delete、Undo、registration next/back/skip/cancelはtouchのみでも完遂可能にする。

### 18.4 Keyboard
主要操作はkeyboardのみで実行可能にする。

- logical tab order
- visible focus indicator
- dialog open時のfocus management
- dialog close時は可能ならtriggerへfocus return
- Escape等のshortcutはdestructive commitを直接実行しない

custom controlを作る場合もnative semantic controlを優先する。

### 18.5 Screen reader / semantics
form inputにはprogrammatic labelを付ける。icon-only buttonにはaccessible nameを付ける。heading/list/table等は意味に合うsemantic structureを使う。

Sync/OFFLINE/AUTH_EXPIRED/RESTORE_LOCKED/validation error等の重要状態はtextとして取得可能にする。

状態変化をARIA live等で通知する場合、network揺らぎやprogress updateを過剰announceしない。

### 18.6 Color / visual
状態やvalidationを色だけで区別しない。text/icon/shape等を併用する。

focus、selected、disabled、error、conflictを視覚的に区別可能にする。

v0.8でWCAG適合認証そのものはrelease必須条件にしないが、主要flowについてcontrastを含む基本accessibility testを実施する。

### 18.7 Text scaling
browser/OS text拡大で主要操作が欠落しない。固定heightによるtext clippingを避ける。

Box.code等のidentity stringは省略表示だけに依存せず、必要時にfull valueを確認可能にする。

### 18.8 Safe area / installed PWA
installed PWA/mobileではnotch/home indicator等のsafe areaを考慮する。

primary actionやUndoをsystem gesture areaへ過度に重ねない。standalone/display-mode差でBusiness機能を変えない。

### 18.9 Camera / QR fallback
camera permission denied、camera unavailable、QR decode failure時もmanual Box.code入力へ到達可能にする。

permission denialをBusiness errorとして扱わず、設定変更またはmanual inputを案内する。

### 18.10 Photo input
mobile camera/gallery、desktop file picker等、platform capabilityに応じたinputを利用可能にする。

source取得方法が違ってもPhoto / Blob canonicalization後のBusiness semanticsは同一。

### 18.11 Print / label fallback
direct print capabilityが無いmobile/PWAでもPDF、次にPNG fallbackへ到達可能にする。

unsupported printerをapplication failureとして扱わない。

### 18.12 Offline startup / install
installed PWAとbrowser tabでoffline behaviorを変えない。cached app shellが利用可能なら同じUser local DBへ到達する。

install不可/拒否でも機能制限しない。update available時もactive operation中に強制reloadしない。

### 18.13 Dialog / destructive action
destructive confirmationはkeyboard/touch/screen readerから同等に理解・操作可能にする。

confirmとcancelのlabelを具体化し、focus defaultだけで誤deleteが起きないようにする。

### 18.14 Baseline verification targets
v0.8 test工程で最低限確認する:

- desktop keyboard-only主要flow
- mobile portrait主要flow
- screen readerで主要form/control/state name取得
- text zoomで主要操作維持
- offline PWA startup
- camera denied -> manual QR fallback
- print unsupported -> PDF/PNG fallback
- update available during active operation
- safe-area / orientation change
- delete confirmation / Photo Undo accessibility

browser/device matrixの具体値はtest設計工程で確定する。

## 21. Box内Item一覧とタグカテゴリ

### 21.1 目的
Box内Item一覧は「この箱に何が入っているか」を把握することを主目的とする。

v0.8ではBox内のtext絞り込み検索を必須機能としない。物から箱を探す用途は全体Item検索を使用する。

### 21.2 Category model
独立した `category` field、primary category、category masterは追加しない。

Itemの既存 `tags` をカテゴリとして利用する。

- Itemは0個以上の複数tagを持てる。
- 1 Itemが複数カテゴリに属してよい。
- tagのcanonicalizationはData Model設計を正とする。
- category専用の追加Business metadataは持たない。

### 21.3 Normal list
通常のBox内Item一覧では各Itemを1回だけ表示し、複数tagによる重複表示を行わない。

通常一覧からItemのtagを確認できる。

### 21.4 Tag category view
カテゴリ表示ではtag単位でItemをグループ化できる。

同じItemが複数tagを持つ場合、そのItemは対応する複数tag groupへ表示されてよい。
これはBusiness recordの複製ではなくview上の重複表示である。

tag無しItemは「タグなし」groupとして扱える。

### 21.5 Sort / grouping policy
v0.8では「代表カテゴリ」を決めて単一カテゴリ順へ並べる方式を採用しない。

Box内の整理手段は:
1. 通常一覧
2. tagによるカテゴリgroup表示

を基本とする。

group内のItem順など、一般的な表示順の細部はtest/UI実装時に一貫したdeterministic orderを定めることができるが、Business semanticsにはしない。

### 21.6 Save boundary
通常一覧、tag category view、表示順変更はread-only UI stateでありBusinessを変更しない。

tag自体を追加・削除した場合のみ通常のItem Business update + Outbox commitとする。

## 20. Screen transition / save-boundary matrix

v0.8全体の最終保存境界を以下とする。

| 操作 | local Business commit | Outbox | server commit | 画面遷移/失敗時 |
|---|---|---|---|---|
| Box新規作成 | Box + DeviceState sequenceをatomic commit | UPSERT同時 | 後続normal Sync | 成功後のみItemsへ |
| Box/Item/Location編集 | entity updateをatomic commit | UPSERT同時 | 後続normal Sync | commit成功後に保存済み表示 |
| Item新規作成 | Item commit | UPSERT同時 | 後続normal Sync | 成功後一覧反映 |
| Item取り出し | boxId=UNASSIGNED update | UPSERT同時 | 後続normal Sync | 成功後即反映 |
| Item delete | tombstone | DELETE同時 | 後続normal Sync | confirm後commit |
| Box delete | child Item UNASSIGNED + Box tombstoneをlogical atomic commit | affected entities同時 | 後続normal Sync | confirm後commit |
| Location delete | child Box UNASSIGNED + Location tombstoneをlogical atomic commit | affected entities同時 | 後続normal Sync | confirm後commit |
| Photo add | blob保存確認後parent update | UPSERT + PhotoUploadState | blob upload後Business Push | commit成功後表示 |
| Photo delete | parent PhotoRef remove | UPSERT | 後続normal Sync | 即反映、10秒Undo |
| Photo Undo | parent PhotoRef再挿入 | UPSERT | 後続normal Sync | Undo commit成功時だけ復帰 |
| Registration Back/Skip | なし | なし | なし | navigationのみ |
| Registration Cancel（Box作成後） | なし | なし | なし | flow終了、既存data保持 |
| Label preview/print/export | なし | なし | なし | Business非変更 |
| Search | なし | なし | なし | local read-only |
| QR local lookup | なし | なし | なし | read-only。online miss確認はnormal Sync |
| Normal Pull | server canonicalをlocal adopt | pending Outboxはreapply/保持 | server read | cursorとadoptをatomic commit |
| Normal Push | responseに応じmetadata/rebase | mutationId一致時のみ削除可能 | operation単位commit | newer local editを失わない |
| Conflict KEEP_SERVER | server snapshot adopt/rebase | newer editなら保持 | Business変更なし | conflict解消後通常Sync |
| Conflict USE_LOCAL | server result adopt/rebase | newer editなら保持 | resolve transaction | conflict解消後通常Sync |
| Full Resync | staging後atomic adopt | 既存Outbox保持 | snapshot readのみ | incomplete stagingをcurrentへ見せない |
| Backup export | なし | なし | なし | foreground read snapshot |
| Restore | server commit前local Business変更なし | Restore専用Outboxなし | server-first atomic apply | COMMITTED後Pull/adopt |
| User switch/logout | なし | なし | session operationのみ | old User DB保持/close |
| PWA update/reload | なし | なし | なし | unsafe operation中はreload延期 |

### 20.1 Final rules
1. navigationだけではBusinessをcommit/rollbackしない。
2. normal Business変更はlocal Business + Outboxを同一logical transactionでcommitする。
3. local commit成功前にUIを保存済み扱いしない。
4. server Sync成功をlocal保存の前提にしない。offlineでもlocal commit可能。
5. reload/back/cancelで既にcommit済みBusinessを暗黙rollbackしない。
6. Restoreだけは例外的にserver-firstであり、server COMMITTED前にRestore結果をlocal Businessへcommitしない。
7. read-only操作（Search/QR lookup/Label preview等）はBusiness save boundaryを持たない。
8. Sync/Conflict responseはmutationId世代を確認し、request後のnewer local editを削除しない。

これによりdesktop/mobile/PWA/offlineで保存境界を共通化する。
