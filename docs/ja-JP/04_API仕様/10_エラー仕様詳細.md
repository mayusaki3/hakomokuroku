# エラー仕様詳細

本書は、全 API に共通するエラー形式・HTTPステータス・ログ方針を正式に定義する。

---

# 1. エラーレスポンス共通形式

```json
{
  "ok": false,
  "error": "error_code"
}
```

---

# 2. error_code 一覧

| error_code | HTTP | 説明 |
|------------|------|------|
| invalid_request | 400 | JSON不正・必須項目不足・型不正 |
| unauthorized | 401 / 200 | 認証不備（Cookieなし/無効）。`/auth/me` は 200 を返す |
| forbidden | 403 | 権限不足。現在は未使用 |
| auth_failed | 400 | email/password が一致しない（詳細を返さない） |
| totp_required | 400 | loginId 未指定・TOTP未完了 |
| totp_failed | 400 | 6 桁コード不一致 |
| not_found | 404 | データが存在しない |
| conflict | 409 | 重複による登録不可（現状未使用） |
| internal_error | 500 | サーバ内部エラー |

---

# 3. 認証エラーの扱い規則

## 3.1 `/api/auth/login` 系

- email/password 不一致はすべて **auth_failed**  
  （「email なし」「password 不一致」を区別しない）

- TOTP 必須ユーザーで loginId が無効  
→ `totp_failed`

---

## 3.2 `/api/auth/me`

- セッションなし  
→ `200` + `{ ok:false, error:"unauthorized" }`

理由：フロント側がエラー扱いせず UI 回収できるため。

---

# 4. Prisma エラーの扱い

- PrismaClientKnownRequestError  
→ `500 internal_error`

- PrismaClientUnknownRequestError  
→ `500 internal_error`

- 期待される DBなし → API 上は `not_found` にマッピング

---

# 5. ログ方針（デバッグ用）

API のレスポンスには内部情報を含めないが、ログには以下を記録してよい：

- Prisma エラー（コード）  
- TOTP コードの一致/不一致（ただし値そのものは記録しない）  
- セッションID の無効化理由  

個人情報（email など）はログに残さないこと。

---

# 6. テスト観点

1. error_code が仕様通りであること  
2. 認証関連 API で **auth_failed** と **unauthorized** を混同しない  
3. `/auth/me` のみ 200 + unauthorized という特殊仕様を持つ  
4. TOTP フローでは  
   - loginId 不正 → totp_failed  
   - コード不一致 → totp_failed  
5. internal_error へのフォールバックが行われること
