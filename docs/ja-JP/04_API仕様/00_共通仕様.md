# 共通仕様（API全体で共通するルール）

本書では、本サービスの API 全体に共通するレスポンス形式・認証方式・エラー方針を定義する。

---

# 1. 共通レスポンス形式

API は原則すべて JSON を返し、成功時は `ok: true`、失敗時は `ok: false` を返す。

## 1.1 成功レスポンス

```json
{
  "ok": true,
  ...（APIごとの追加フィールド）
}
```

### 例
- `/api/auth/login`（通常ログイン）  
```json
{
  "ok": true,
  "user": { "id": "xxx", "displayName": "..." }
}
```

- `/api/auth/login`（TOTP 必須ユーザー）  
```json
{
  "ok": true,
  "totpRequired": true,
  "loginId": "xxxx"
}
```

---

# 2. エラー形式

## 2.1 共通エラーフォーマット

```json
{
  "ok": false,
  "error": "error_code"
}
```

## 2.2 主なエラーコード定義

| errorコード | 意味 |
|-------------|------|
| invalid_request | 入力不備・バリデーションエラー |
| unauthorized | 認証情報が存在しない／無効 |
| auth_failed | email/password が一致しない（詳細は隠す） |
| forbidden | 権限不足 |
| not_found | 対象データなし |
| internal_error | サーバ内部エラー |

**重要**  
- `auth_failed` は *常に同じレスポンス* を返し、  
  「email 不一致 or password 不一致」をクライアントが区別できないようにする。

---

# 3. 認証方式

本サービスは以下の 2 種類の認証方式を持つ。

## 3.1 開発モード（dev-token 認証）

ヘッダー例：

```text
Authorization: Bearer devtoken
```

`requireUserId()` により固定の開発ユーザー（seed で投入されるユーザー）として扱われる。

---

## 3.2 セッション Cookie 認証（本番想定）

- `/api/auth/login` 成功時に `Set-Cookie` でセッション ID を発行
- 認証必須 API（例：`/api/auth/me`, `/api/settings/user` など）は Cookie を基にユーザー判定

Cookie は本番環境で以下を要求：
- HttpOnly
- Secure
- SameSite=Lax もしくは Strict

---

## 3.3 TOTP 認証（2段階認証）

TOTP 有効ユーザーは通常ログイン後、次のステップを踏む：

1. `/api/auth/login`  
   - `totpRequired: true` と `loginId` を返す  
   - セッション Cookie は発行されない
2. `/api/auth/login/totp`  
   - loginId と 6 桁コードを送信  
   - 検証成功後にセッション Cookie を発行

---

# 4. バリデーション方針

| 種類 | 方針 |
|------|------|
| 必須項目 | 未指定の場合は `400 invalid_request` |
| メール形式 | 簡易チェックを行う |
| JSON不正 | `400 invalid_request` |
| パスワード | ログに書き出さない |

---

# 5. セキュリティ方針

- 認証失敗時は詳細を返さない  
  （例：email か password のどちらが誤りかは出さない）
- TOTP の失敗回数に応じて `totpFailCount` や `lockUntil` を利用可能
- TOTP 秘密鍵・Vision APIキーは暗号化保存
- セッション Cookie の設定はセキュア属性を必須とする（本番）
