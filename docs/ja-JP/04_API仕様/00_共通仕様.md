# 共通仕様（API全体で共通するルール）

本書では、本サービスの API 全体に共通する  
**レスポンス形式・認証方式・エラー方針** を定義する。

---

## 1. 共通レスポンス形式

API は原則として JSON を返却する。  
ただし、成功時にレスポンスボディを持たない API は 204 No Content を返却する。

- 成功時：`ok: true`
- 失敗時：`ok: false`

を必ず含める。

### 1.1 成功レスポンス

```json
{
  "ok": true,
  "...": "API ごとの追加フィールド"
}
```

### 例

#### `/api/auth/login`（通常ログイン）

```json
{
  "ok": true,
  "user": {
    "id": "xxx",
    "displayName": "..."
  }
}
```

#### `/api/auth/login`（TOTP 必須ユーザー）

```json
{
  "ok": true,
  "totpRequired": true,
  "loginId": "xxxx"
}
```

## 1.2 204 No Content の扱い（共通）

状態変更 API のうち、成功時にレスポンスボディが不要なものは `204 No Content` を返す。
この場合、`ok: true` 等の JSON ボディは返さない。

例：
- `/api/auth/tokens/revoke`（204）
- `/api/auth/tokens/revokeAll`（204）
- `/api/auth/totp/disable`（204）

## 1.3 ok フラグを返す API / 返さない API（共通）

- 成功時にクライアントが利用するデータを返す API は、`200` で JSON を返し、`ok: true` を含める。
  - 例：`/api/auth/login`（challengeId / totpRequired 等）、`/api/auth/totp/verify`（recoveryCodes）、`/api/auth/totp/setup`（otpauthUrl）
- 成功時にレスポンスボディが不要な API は、`204 No Content` を返し、JSON を返さない。
  - 例：`/api/auth/tokens/revoke`、`/api/auth/tokens/revokeAll`、`/api/auth/totp/disable`

---

## 2. エラー形式

### 2.1 共通エラーフォーマット

```json
{
  "ok": false,
  "error": "error_code"
}
```

### 2.2 主なエラーコード定義

| error コード | 意味 |
|-------------|------|
| invalid_request | 入力不備・バリデーションエラー（形式不正・必須項目不足など） |
| unauthorized | 認証情報が存在しない／無効（未ログイン・セッション無効） |
| auth_failed | 認証失敗（ID/パスワード不一致、TOTPコード不一致 等。詳細は秘匿） |
| forbidden | 権限不足（認可エラー） |
| not_found | 対象データなし |
| conflict | 現在の状態では実行できない（状態不正） |
| internal_error | サーバ内部エラー |

**重要事項**

- `auth_failed` は **常に同一レスポンス** を返す  
  - ID / パスワード不一致  
  - TOTP コード不一致  
  - リカバリコード不一致  
  など、**認証に関する失敗理由は区別しない**
- クライアントは  
  「何が間違っていたか」を推測できないものとする

## 3. 認証方式

本サービスは以下の認証方式を採用する。

### 3.1 開発モード（dev-token 認証）

ヘッダー例：

```text
Authorization: Bearer devtoken
```

- `requireUserId()` により固定の開発用ユーザーとして扱う
- 主にローカル開発・テスト用途

---

### 3.2 セッション Cookie 認証（本番想定）

- `/api/auth/login` 成功時に `Set-Cookie` でセッション ID を発行
- 認証必須 API（例：`/api/auth/me`, `/api/settings/user`）は Cookie を基に認証

本番環境では Cookie に以下を要求する：

- HttpOnly
- Secure
- SameSite=Lax または Strict

---

### 3.3 TOTP 認証（2 段階認証）

TOTP 有効ユーザーは、以下のフローを踏む。

1. `/api/auth/login`
   - `totpRequired: true` と `loginId` を返却
   - この時点ではセッション Cookie は発行しない
2. `/api/auth/login/totp`
   - `loginId` と TOTP コードを送信
   - 検証成功時にセッション Cookie を発行

---

## 3.4 リカバリコード運用方針（共通）

TOTP を有効化したユーザーには、リカバリコード（recoveryCodes）を発行する。

- 発行:
  - `/api/auth/totp/verify` 成功時に **10個発行**し、レスポンスで **平文を1回だけ返す**
  - 「再発行 API（/api/auth/totp/recovery/reissue）は提供するが、平文返却は再発行時のみ（都度1回）」に変更
- 保存:
  - DB には `User.recoveryCodes` に保存する（形式は実装に合わせる。推奨はハッシュ化し、平文は保持しない）
- 使用:
  - `/api/auth/login/totp` および `/api/auth/totp/disable` で使用できる
  - **使用したコードは必ず失効**し、`recoveryCodes` から除去する（1回限り）
- 残数:
  - `/api/auth/totp/status` は残数（recoveryRemain）のみ返す
- 再発行:
  - 再発行 API は **TOTP による本人確認が必須**であり、
    有効な TOTP 秘密鍵を持たないユーザーは実行できない

---

## 4. バリデーション方針

| 種類 | 方針 |
|------|------|
| 必須項目 | 未指定の場合は 400 invalid_request |
| メール形式 | 簡易形式チェックのみ |
| JSON 不正 | 400 invalid_request |
| パスワード | ログ出力・レスポンスに含めない |

---

## 5. セキュリティ方針

- 認証失敗時は詳細理由を返さない
- TOTP の失敗回数に応じて以下を利用可能
  - `totpFailCount`
  - `lockUntil`
- 以下の機密情報は暗号化して保存する
  - TOTP 秘密鍵
  - Vision API キー
- セッション Cookie は本番環境で Secure 属性必須
