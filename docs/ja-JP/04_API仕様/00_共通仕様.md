# 共通仕様（API全体で共通するルール）

本書では、本サービスの API 全体に共通する  
**レスポンス形式・認証方式・エラー方針** を定義する。

---

## 1. 共通レスポンス形式

API は原則として JSON を返却する。

- 成功時：`ok: true`
- 失敗時：`ok: false`

を必ず含める。

### 1.1 成功レスポンス

```json
{
  "ok": true,
  "...": "API ごとの追加フィールド"
}
```

### 例

#### `/api/auth/login`（通常ログイン）

```json
{
  "ok": true,
  "user": {
    "id": "xxx",
    "displayName": "..."
  }
}
```

#### `/api/auth/login`（TOTP 必須ユーザー）

```json
{
  "ok": true,
  "totpRequired": true,
  "loginId": "xxxx"
}
```

---

## 2. エラー形式

### 2.1 共通エラーフォーマット

```json
{
  "ok": false,
  "error": "error_code"
}
```

### 2.2 主なエラーコード定義

| error コード | 意味 |
|-------------|------|
| invalid_request | 入力不備・バリデーションエラー |
| unauthorized | 認証情報が存在しない／無効 |
| auth_failed | ID / パスワード不一致（詳細は秘匿） |
| forbidden | 権限不足 |
| not_found | 対象データなし |
| internal_error | サーバ内部エラー |

**重要事項**

- `auth_failed` は **常に同一レスポンス** を返す  
- 「ID が違う / パスワードが違う」をクライアントが区別できないようにする

---

## 3. 認証方式

本サービスは以下の認証方式を採用する。

### 3.1 開発モード（dev-token 認証）

ヘッダー例：

```text
Authorization: Bearer devtoken
```

- `requireUserId()` により固定の開発用ユーザーとして扱う
- 主にローカル開発・テスト用途

---

### 3.2 セッション Cookie 認証（本番想定）

- `/api/auth/login` 成功時に `Set-Cookie` でセッション ID を発行
- 認証必須 API（例：`/api/auth/me`, `/api/settings/user`）は Cookie を基に認証

本番環境では Cookie に以下を要求する：

- HttpOnly
- Secure
- SameSite=Lax または Strict

---

### 3.3 TOTP 認証（2 段階認証）

TOTP 有効ユーザーは、以下のフローを踏む。

1. `/api/auth/login`
   - `totpRequired: true` と `loginId` を返却
   - この時点ではセッション Cookie は発行しない
2. `/api/auth/login/totp`
   - `loginId` と TOTP コードを送信
   - 検証成功時にセッション Cookie を発行

---

## 4. バリデーション方針

| 種類 | 方針 |
|------|------|
| 必須項目 | 未指定の場合は 400 invalid_request |
| メール形式 | 簡易形式チェックのみ |
| JSON 不正 | 400 invalid_request |
| パスワード | ログ出力・レスポンスに含めない |

---

## 5. セキュリティ方針

- 認証失敗時は詳細理由を返さない
- TOTP の失敗回数に応じて以下を利用可能
  - `totpFailCount`
  - `lockUntil`
- 以下の機密情報は暗号化して保存する
  - TOTP 秘密鍵
  - Vision API キー
- セッション Cookie は本番環境で Secure 属性必須
