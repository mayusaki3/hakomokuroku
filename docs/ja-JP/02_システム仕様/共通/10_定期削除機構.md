# 共通定期削除機構

## 1. 適用範囲

サーバー側の期限に基づく定期削除全般に適用する。通知、Business tombstone、同期履歴、通常ログ、期限切れ・失効済みセッション、未参照Blob・設定用画像等を対象とする。保持期間、起算日時、削除条件は個別仕様を正本とする。クライアントGC、即時削除、業務トランザクション内の削除は対象外。

## 2. 登録とスケジュール

アプリケーションプロセス内でWeb/APIリクエストとは独立した非同期処理として実行する。専用ワーカー、管理UI、動的ジョブ設定DBは設けない。

ジョブはコードで静的登録する。論理的な登録情報は以下とする（実装上の型・名称は別途設計）。

| 属性 | 内容 |
|---|---|
| jobId | 一意な固定識別子 |
| schedule | UTC実行スケジュール |
| batchSize | 1バッチの最大処理件数 |
| leaseDuration | リース期間、既定60秒 |
| executeBatch | 個別バッチ処理 |

停止中の実行予定は起動時に補完しない。失敗時は次回定期実行で再処理する。期限判定やAPIの有効性はジョブの実行状況に依存させない。

## 3. 排他制御

同一ジョブの多重実行を禁止し、異なるジョブの同時実行を許容する。共通リース管理の論理属性は jobId（主キー）、ownerId（実行単位UUID）、leaseUntil（UTC期限）とする。

- 取得・更新・解放は原子的に実行する。
- 未取得または期限切れのリースを取得可能とする。有効な他所有者のリースがある場合は実行をスキップする。
- バッチ開始前に所有権と期限を確認して更新する。独立した定期更新タイマーは使用しない。
- 所有権喪失時は後続バッチを禁止する。旧所有者は新所有者のリースを更新・解放できない。
- DB削除バッチでは所有権・期限の検証と削除を同一書き込みトランザクションで保護し、確定前にも検証する。無効ならロールバックする。
- 異常終了時は期限切れにより再取得可能とする。ファイル操作を含むバッチの安全性は個別仕様で保証する。

## 4. バッチ実行

共通機構はリース取得、バッチ前更新、個別バッチ呼出し、継続・終了判定、リース解放、ログ記録を担当する。個別ジョブは対象選定、削除条件の再確認、トランザクション境界、関連データの整合性を担当する。

バッチ結果は確定削除件数と後続処理の有無を返す。バッチ分割が不要な処理は1回で終了可能とする。失敗時は後続処理を中止し、確定済みバッチを維持する。別ジョブの実行には原則として影響させない。

## 5. 実行ログ

既存の通常ログを利用し、ジョブID、実行識別子、開始・終了UTC日時、確定削除件数、結果、失敗時のエラーを記録する。削除件数0でも実行結果を記録する。専用履歴テーブルは設けない。

## 6. ファイルを含む削除

写真Blob・設定用画像は通常未参照状態と論理削除状態を区別する。期限到達後の参照なし確認と論理削除確定を、参照追加と排他的なDBトランザクションで行う。論理削除済みデータへの参照追加は禁止する。追加保持期間を設けず物理削除可能とし、失敗時は論理削除状態を維持して次回再処理する。独立した削除予約機構は設けない。通知等に論理削除を強制しない。

### 6.1 共通ファイル排他

単一ホスト・ローカルファイルシステムを前提とする。固定256分割のOS排他ロックを写真Blob・設定用画像で共用する。対象種別、userId、対象IDの曖昧性のない符号化と安定ハッシュで分割を決定する。具体的な符号化・配置は詳細設計で定め、全プロセスで統一する。ロックファイルは稼働中に削除・置換しない。

- 同一プロセス内および複数プロセス間で排他を保証する。OSロックはリース期限で解除せず、全ファイル操作の完了後に解放する。プロセス終了時の自動解除を検証する。
- ファイル作成、置換、再upload、Restore、staging cleanup、物理削除は同一対象について同じ排他規則に従う。ロック取得後に最新DB状態を確認する。DB書き込みトランザクションを保持したままロック取得を待たない。
- 定期削除は非待機取得とし、競合対象をスキップする。同一実行内で競合対象を無限に再選択しない。複数ロックが不可避な場合は番号順に重複なく取得する。
- 論理削除確定は参照追加と排他的なDBトランザクションで行う。物理削除は論理削除確定後に実行し、ファイル操作中にDB書き込みトランザクションを保持しない。論理削除状態から通常状態への復帰は禁止する。
- 物理削除直前に論理削除状態・参照不存在・リースを再確認する。リース喪失後は新規ファイル操作を開始せず、開始済み操作の完了を待つ。DB削除はリース検証付き書き込みトランザクションで行い、失敗時は論理削除状態を維持する。
- 同一IDの再uploadは物理削除と管理レコード削除の完了後に許可する。追加のstorageId、削除予約テーブルは設けない。

実装候補は fs-ext-extra-prebuilt とするが採用確定はWindows/Linux、同一プロセス内・プロセス間排他、異常終了、リース喪失、再upload競合の検証後とする。

## 7. 個別仕様と残件

通知は毎日18:00 UTC、最大500件/バッチとする。保存期限とAPI上の扱いは通知固有仕様に従う。

各ジョブの未決定スケジュール、具体的DB型、ファイルの論理削除属性、具体的なファイル排他実装と個別処理の詳細は第6.1節に従い詳細設計で確定する。これらの安全性が確定するまで該当ファイル削除ジョブを実装しない。複数プロセスで同一予定時刻の逐次重複実行を防ぐ具体方式も詳細設計で確認する。
