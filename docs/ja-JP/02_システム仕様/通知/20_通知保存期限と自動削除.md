# 通知保存期限と自動削除

## 1. 適用範囲

全通知種別に適用する。通知の状態・識別子は[通知データモデル](./10_通知データモデル.md)、定期実行・排他・復旧・ログの共通仕様は[共通定期削除機構](../共通/10_定期削除機構.md)に従う。

## 2. 保存期限

- 未確認（readAt がNULL）は期限なし。
- 確認済みは readAt + 720時間 を期限とし、サーバー現在時刻が期限以上なら期限切れとする。UTCミリ秒精度で判定する。
- createdAt は起算点としない。expiresAt 等の専用列は設けない。
- 再確認によって既存readAtを更新しない。期限内の未確認への変更でreadAtをNULLにし、再度確認済みにした日時から期限を算出する。
- 期限切れ後は未確認へ戻せない。物理削除の遅延によって有効期限を延長しない。

## 3. API上の扱い

期限切れ通知は物理削除前でも一覧・件数集計から除外する。詳細取得、状態変更、個別手動削除は物理削除済みと同じ404 Not Foundとする。一括操作では対象外としてスキップし、処理件数と対象外件数を返す。ログイン、一覧取得、期限切れ通知へのAPIアクセスを契機とした物理削除は行わない。

状態変更と削除の競合時は実際の変更・削除時点で条件を再検証する。

## 4. 個別ジョブ設定

| 項目 | 設定 |
|---|---|
| 実行時刻 | 毎日18:00 UTC |
| バッチ上限 | 500件 |
| リース期間 | 共通既定値60秒 |
| 削除順序 | readAt ASC, userId ASC, id ASC |

利用者のログイン有無に依存しない。停止中の補完実行および失敗直後の再試行は行わず、次回定期実行に委ねる。

## 5. バッチ処理

各バッチは独立したDBトランザクションとし、期限切れ条件に合致する通知を上記順序で最大500件選択する。削除時にreadAtと期限条件を再確認し、複合識別子(userId, id)で対象を特定する。リース検証・確定・失敗時の扱いは共通仕様に従う。削除対象がなくなれば終了する。確定済みバッチは後続失敗時も維持する。

期限判定用にreadAt単独インデックスを使用する。複合削除順序用インデックスは追加せず、必要な追加ソートを許容する。EXPLAIN QUERY PLANと実測で妥当性を検証する。

## 6. 関連データ

通知の自動削除はItem、Vision認識結果、説明、タグ、認識完了状態を変更せず、再認識を起動しない。Item論理削除時の関連通知削除と物理削除時のCASCADEは通知データモデルに従い、定期削除とは分離する。

## 7. 検証対象

期限直前・一致・直後、未確認・再確認、APIと削除の競合、500件境界、複数ユーザーでの安定順序、部分失敗、リース喪失、削除件数0、関連データ不変性、インデックス利用をテスト仕様で定義する。
