# 通知データモデル

## 1. 目的と適用範囲

本書は箱目録の通知データについて、確定済みの保存主体、利用者境界、状態、日時、関連データとの関係および保存期限の整合性を定義する。

通知の識別単位と複合主キーは第3章で確定する。その他のDBカラム名・型・インデックス・通知本文の構造は、未決定事項として区別する。本書に記載した論理属性名を、そのまま実装上のカラム名として確定したものとは扱わない。

## 2. 保存主体と同期境界（2026-11-09確定）

- 通知データの正本はサーバーDBに置く。
- 複数端末はAPIを介して同一の通知データを参照する。
- 確認状態の変更と削除はサーバーで確定し、他端末からの取得結果にも反映される。
- オフライン中の通知の確認状態変更・削除は受け付けない。端末側で保留した変更を後からBusiness同期する仕組みは設けない。
- 通知データは既存のBusiness同期モデルに含めない。
- 一覧の表示件数、並び順、絞り込み条件のみ端末ごとにローカル保存し、サーバーへのユーザー設定同期は行わない。

## 3. 通知の識別子・ユーザー境界と論理属性

### 3.1 識別子と所有者（2026-11-09確定）

- 通知の識別単位は `(userId, id)` とし、DBの主キーを `PRIMARY KEY (userId, id)` とする。
- `userId` は通知所有者の `User.id` を参照する。`id` は同一ユーザー内で一意とし、異なるユーザー間では同一値を許可する。
- APIは認証済みユーザーから `userId` を決定し、通知 `id` と組み合わせて対象を特定する。クライアント指定の `userId` を認可根拠としない。
- 通知ID `id` はサーバーでUUID v4として生成する。DB上の識別単位は引き続き `(userId, id)` とする。
- INSERT時の一意性はDBの複合主キー制約で保証し、事前の重複確認のみには依存しない。
- INSERTで通知の複合主キー衝突と識別できた場合のみ、UUID v4を再生成して再試行する。その他の制約違反では再採番しない。
- 初回INSERTを含め最大3回試行する。上限到達時は通知作成失敗としてログに記録する。
- UUID生成時にユーザー別連番カウンターや採番用排他ロックは使用しない。

### 3.2 その他の論理属性

| 論理属性 | 意味・確定済みの制約 | 詳細設計の状態 |
|---|---|---|
| 通知識別子 | `id`。サーバー生成UUID v4。`(userId, id)` の組合せで通知を一意に識別する | 確定済み |
| 利用者との関連 | `userId`。`User.id` を参照し、複合主キーの一部とする | 外部キーの物理実装詳細は未確定 |
| 通知種別 | 通知の発生元・用途を表す。Vision後追い認識完了通知は対象に含む | 型、種別コード、他の通知種別は未確定 |
| 通知内容 | 利用者に表示する通知情報 | タイトル・本文等の構造は未確定 |
| 作成日時 | 通知一覧の新しい順・古い順の基準 | 同一日時の場合の安定ソート規則は未確定 |
| 確認状態 | 未確認／確認済み | 永続表現（列・列挙値）は未確定 |
| 確認日時 | 確認済みとなった日時。削除期限の起算点 | 列名・格納型は未確定 |
| 関連先 | Vision完了通知から対象Itemの編集画面へ遷移するための情報 | 参照方法、対象削除時の扱いは未確定 |

確認状態と確認日時の論理整合性は第4章に定義する。通知の物理削除後の参照は通常の存在しない通知として扱う。

## 4. 状態遷移と日時の整合性

| 現在状態 | 操作 | 結果 | 確認日時・期限 |
|---|---|---|---|
| 未確認 | 一覧表示 | 未確認のまま | 確認日時を設定しない |
| 未確認 | 個別通知を開く | 確認済み | 操作時の確認日時を記録し、720時間後に期限切れ |
| 未確認 | 一括確認済み | 確認済み | 処理時の確認日時を記録し、720時間後に期限切れ |
| 確認済み（期限内） | 個別通知を再度開く／一括確認済み | 確認済みのまま | 既存の確認日時を維持し、期限を延長しない |
| 確認済み（期限内） | 明示的な未確認操作／一括未確認 | 未確認 | 削除期限を解除する |
| 未確認に戻した通知 | 再度開く／一括確認済み | 確認済み | 新たな確認日時を記録し、そこから720時間 |
| 確認済み（期限切れ） | 詳細取得・状態変更・手動削除 | 操作不可 | 404 Not Found。未確認への復帰不可 |
| 有効な通知 | 手動削除／一括削除 | 削除 | 関連するItem・Vision処理には影響しない |

- 確認日時を起算点とする30日（720時間）の期限は、通知作成日時とは無関係に判定する。
- 期限切れは論理的な有効性判定であり、物理削除ジョブの実行状況に依存しない。
- 期限切れ通知は一覧と件数集計から除外する。
- 一括操作は有効な対象だけを処理し、対象外はスキップする。処理件数と対象外件数のみ返すという利用者向け方針を維持する。
- 削除と状態変更の競合時は、削除対象条件を実際の削除時点で再検証する。

## 5. Vision完了通知と関連データ

- 後追い認識が完了したItemごとに通知を生成する。複数Itemの完了を一つの通知に集約しない。
- 認識結果のItemへの自動反映は、通知の確認や承認を条件としない。
- 通知から関連Itemの編集画面へ直接移動できることを要件とする。
- 通知の確認状態変更、手動削除、期限切れによる自動削除は、Itemの説明・タグ、認識結果、認識処理の完了状態を変更しない。
- 通知の削除を契機としてVision認識を再実行しない。
- 関連Itemが後から削除された場合の遷移先・通知の扱いは未確定であり、詳細設計で判断する。

## 6. データ整合性と実装境界

- サーバーが通知の確認状態・確認日時・期限判定を一元的に扱う。
- 期限切れの通知は、物理削除されるまでDBに残っていてもAPI上は削除済み通知と同様に扱う。
- サーバーの定期削除ジョブは毎日18:00 UTCに実行する。排他リース、500件以下の独立バッチ、実行ログ等の詳細は `20_通知保存期限と自動削除.md` で定義する。
- 既存の[DBスキーマ定義](../../02_アーキテクチャ/40_DBスキーマ定義.md)と同じ `(userId, id)` の複合識別子を採用する。ただし、Business同期用の属性や同期処理は通知に流用しない。
- 通知APIでは認証済みユーザーの `userId` を用いてユーザー間の参照を防止する。認可エラー応答とDB参照制約の詳細はAPI・DB詳細設計で定義する。

## 7. 未決定事項

以下は本書作成時点で確定しない。

1. 通知IDの形式・生成主体・衝突時再試行は確定済み。UUID格納型とDBエラー識別の実装詳細は未確定。
2. 通知種別・本文・遷移先情報のカラム構成とデータ型。
3. 確認状態・確認日時の物理表現、保存日時の精度。
4. 作成日時が同一の場合の安定ソートキー。
5. 関連Itemが削除された際の通知の表示・遷移動作。
6. 必要なインデックス、トランザクション境界、APIの具体的な入出力。

これらは別途承認を得てから確定する。
