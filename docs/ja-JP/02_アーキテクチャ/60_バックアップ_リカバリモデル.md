# バックアップ / リカバリモデル

## 1. 目的

箱目録のバックアップ / リカバリは、利用者が管理する業務データを自己完結したバックアップファイルとして保存し、同じUser（利用者）の環境へ安全に復元するための仕組みである。

本書ではバックアップ対象、復元単位、サーバーとの整合、デバイス固有情報との分離を定義する。

DB上の個々のテーブルや補助スキーマは [データモデル / DBスキーマ定義](./40_DBスキーマ定義.md) で定義する。

## 2. 対象となるデータ

バックアップ対象はUserに属する業務データ。

- Box（箱情報）
- Item（物品情報）
- BoxLocation（箱の場所情報）
- 各業務データに属する写真
- バックアップ時点で端末内に存在する未同期の業務変更

バックアップはサーバー上の同期済みデータだけを複製するものではない。端末内の未同期Businessデータも含め、利用者の業務データを失わないことを優先する。

## 3. 対象外

以下は通常バックアップへ含めない。

- Device（デバイス）管理情報
- DevicePrefix（デバイス接頭辞）
- DeviceState（ローカルデバイス状態）
- LocalSequence（ローカル連番）
- SyncState
- Outboxそのもの
- SyncConflictの管理状態
- RestoreLock等のサーバー制御状態

これらは業務データそのものではなく、特定環境・デバイス・同期処理に属する状態である。

既存Box.code（箱コード）はBoxの業務データとしてバックアップ対象とし、Restore（リストア）時に変更しない。

## 4. バックアップファイル

バックアップ形式:

```text
schema: hakomokuroku-backup
version: 1
extension: .hkmbackup
container: ZIP
```

バックアップファイルは自己完結型とし、復元に必要な業務データと対象写真をファイル内へ含める。

バックアップは作成元Userを識別できる情報を持ち、別UserへのRestoreは許可しない。

## 5. Restore（リストア）の基本原則

Restoreは同一Userに対してのみ行う。

Restoreで次を行わない。

- Box.codeの自動再採番
- DeviceStateの復元
- DevicePrefixの再利用
- データ競合の無条件上書き
- 不正なBox親子関係の自動修復

Restoreデータと現在データを比較し、安全に自動決定できない競合は利用者確認へ回す。

## 6. Restore前検証

少なくとも次を検証する。

- backup schema / version
- User一致
- 必須データの形式
- Box.codeのcanonical形式
- 同一Box.idに異なるBox.codeが存在しない
- 異なるBox.idで同一Box.codeが重複しない
- Box（箱情報）の親子関係にself-reference / cycleがない
- Item（物品情報）のBox参照が有効、または未割当（UNASSIGNED = null）
- Box（箱情報）のBoxLocation参照が有効、または未割当（UNASSIGNED = null）

不正データを自動補正してRestoreを続行しない。

## 7. サーバー優先のRestore

Restoreはserver canonicalとの整合を維持するため、server側で適用を管理する。

基本フロー:

1. Restore対象ファイルを検証する。
2. serverでRestore lockを取得する。
3. current server Businessとbackup Businessを比較する。
4. 競合があれば利用者へ最終適用内容を確認する。
5. applyIdを指定してRestore applyを実行する。
6. server transactionでBusiness変更と同期履歴をcommitする。
7. RestoreApplyResultをCOMMITTEDとして記録する。
8. clientはserverからPullし、commit済みcanonical stateを採用する。
9. 必要なlocal未同期変更を通常の同期規則で再適用する。

Restore中にclientだけを正としてserver stateを直接置換しない。

## 8. Restore lock

Restore中に同じUserのserver Businessが並行更新され、検証済みRestore planが無効になることを防ぐためRestore lockを使用する。

- lock有効時間: 60秒
- clientは20秒間隔を目安にrenew
- server clockを正とする
- raw lock tokenはDBへ保存せずhashを保存する
- lock失効後のapplyは拒否する

Restore中のDevice register / DevicePrefix allocationも一時停止する。

## 9. applyIdと冪等性

Restore applyにはclient生成のapplyIdを使用する。

serverはUser + applyId単位でRestoreApplyResultを保持する。

同じapplyIdのretryでは二重適用しない。

同じapplyIdで異なるrequestが送られた場合はrequestDigest不一致として拒否する。

commit済みRestoreApplyResultは7日保持する。

## 10. 競合

backupとcurrent serverの双方に変更があり、自動的に一方を選択できない場合は利用者確認を要求する。

特に次は自動修復しない。

- 同一Box.idでBox.codeが異なる
- 異なるBox.idでBox.codeが重複する
- 現在データとbackupの組合せでBox nesting cycleが発生する
- 参照先の選択によって業務上の意味が変わる

利用者が選択した最終planについても、apply直前にcurrent server stateを再検証する。

## 11. 新しい環境へのRestore

新しいPC / スマートフォン等へRestoreした場合、DeviceStateはbackupから復元しない。

Restore完了後:

1. Businessデータをserver canonicalから取得する。
2. local DeviceStateが存在しなければnew device setupを行う。
3. new deviceIdを生成する。
4. serverからnew DevicePrefixを取得する。
5. LocalSequenceを0から開始する。

Restoreされた既存Box.codeはそのまま維持する。

## 12. DBスキーマとの関係

本モデルを実現するため、server DBでは主に次の補助データを使用する。

- RestoreLock
- RestoreApplyResult
- SyncChangeLog
- SyncConflict
- FullResyncSnapshot / FullResyncSnapshotEntity

各field、key、retention、transaction boundaryは [データモデル / DBスキーマ定義](./40_DBスキーマ定義.md) を参照。
