# Sync設計

## 1. 基本原則
server canonical stateとlocal offline BusinessをOutbox方式で収束させる。

通常sync:
```text
Pull → Outbox reapply → Push → Pull
```

Business updateとOutbox writeは同一IndexedDB transaction。

## 2. Push conflict
```text
baseRevision == server.revision
  → normal update

baseRevision != server.revision
  → contentHash same: UNCHANGED
  → contentHash different: CONFLICT
```

updatedAtの新旧でwinnerを決めない。

## 3. Pull
SyncChangeLogをcanonical sourceとし、DB-wide monotonic signed 64-bit `syncSeq` をcursorに使用する。User scopeで `syncSeq > cursor` を取得する。

SyncChangeLog retentionは90日。cursorが保持範囲外なら `FULL_RESYNC_REQUIRED`。

## 4. Tombstone
server accepted DELETE後30日を経過したtombstoneはphysical deletion可能。offline未Push deleteはlocalで保持する。

## 5. Full Resync
- fixed `snapshotSeq`
- entity typeごとにpaging
- stagingへ構築
- staging完成後のみadopt
- local Outboxを保持
- adopt後Outboxをreapply

Outbox reapply order:
```text
BoxLocation → Box → Item
```

## 6. SyncConflict
SyncConflictはaudit historyではなく未解決状態の一時領域。解決時にserver revisionを再確認し、staleなら最新server snapshotと再比較する。

## 7. Restore lock中
非owner device/sessionの以下をretryable `RESTORE_LOCKED`としてpauseする。
- Business Pull
- Business Push
- Business-related original/thumbnail upload
- server photo reference confirmation

local閲覧・Business編集は継続しOutboxへ記録する。unlock後は通常syncへ戻す。

## 8. Wire format共通規則
- endpointは `/api/sync/push`, `/api/sync/pull`
- authenticated Userはsession/tokenからserverが確定し、requestのuserIdを信用しない
- `revision`, `syncSeq`, cursor等のsigned 64-bit値はJSON **decimal string** で送受信する
- timestampはRFC3339
- entity typeは `BOX | ITEM | BOX_LOCATION`
- error responseはmachine-readable `code` を必須とする
- unknown fieldはv0.8ではvalidation errorとし、暗黙にBusiness contentへ取り込まない

## 9. Push API

### 9.1 Request
`POST /api/sync/push`

```json
{
  "operations": [
    {
      "operationId": "client-generated-id",
      "entityType": "BOX",
      "entityId": "box-id",
      "operation": "UPSERT",
      "baseRevision": "12",
      "contentHash": "sha256-hex",
      "payload": {}
    }
  ]
}
```

rules:
- `operationId` はrequest内unique。response対応付け用でBusiness identityではない
- `entityId` とpayload内identityがある場合は一致必須
- `operation` は `UPSERT | DELETE`
- DELETEもcanonical deleted Business payload/contentHashを送る
- request内operation順をserver commit順として保証しない
- clientはdependency順 `BoxLocation → Box → Item` で送る
- 1 request最大100 operations
- payload最大サイズは通常HTTP/API制限に従う。photo binaryは含めない

### 9.2 Per-operation processing
各operationは独立logical transaction。

```text
entity不存在 + baseRevision=0 + UPSERT
  → CREATE/APPLIED

entity不存在 + その他
  → NOT_FOUND または CONFLICT相当

entity存在 + baseRevision == server.revision
  → validate → APPLIED

entity存在 + baseRevision != server.revision
  + contentHash == server.contentHash
    → UNCHANGED
  + contentHash != server.contentHash
    → CONFLICT
```

Box.code immutable違反、reference不存在、photo未confirm等はAPPLIEDにしない。

### 9.3 Response
HTTP 200は「request envelopeを処理できた」を意味し、全operation成功を意味しない。

```json
{
  "results": [
    {
      "operationId": "client-generated-id",
      "entityType": "BOX",
      "entityId": "box-id",
      "status": "APPLIED",
      "revision": "13",
      "contentHash": "sha256-hex",
      "syncSeq": "901",
      "serverUpdatedAt": "2026-09-27T00:00:00.000Z"
    }
  ]
}
```

status:
- `APPLIED`: server Business変更commit済み。Outbox削除可能
- `UNCHANGED`: server canonical contentが同一。server metadataを採用しOutbox削除可能
- `CONFLICT`: SyncConflict作成/更新。Outboxは解決まで保持
- `REJECTED`: validation/reference/photo等の恒久的error。Outboxを自動削除しない

CONFLICT resultには:
```json
{
  "status": "CONFLICT",
  "conflictId": "...",
  "serverRevision": "13",
  "serverContentHash": "...",
  "serverPayload": {}
}
```
を含める。

REJECTED resultには `error.code`, `error.message`, optional `error.field` を含める。

### 9.4 Push request-level errors
request-level errorはoperationを処理開始できない場合。

- `400 INVALID_REQUEST`
- `401 AUTH_REQUIRED`
- `403 USER_SCOPE_VIOLATION`
- `409 RESTORE_LOCKED` retryable
- `413 REQUEST_TOO_LARGE`
- `500 INTERNAL_ERROR`
- `503 TEMPORARILY_UNAVAILABLE` retryable

request-level failureではclientはそのrequestのOutboxを削除しない。

### 9.5 REJECTED codes
最低限:
- `VALIDATION_ERROR`
- `ENTITY_NOT_FOUND`
- `REFERENCE_NOT_FOUND`
- `RESERVED_ENTITY`
- `IMMUTABLE_FIELD`
- `BOX_CODE_CONFLICT`
- `PHOTO_NOT_READY`
- `PHOTO_PARENT_CONFLICT`
- `BOX_PARENT_NOT_FOUND`
- `BOX_PARENT_CYCLE`
- `BOX_LOCATION_PARENT_CONFLICT`


## 9.6 Box parent reference validation

Box payloadに `parentBoxId` がある場合、serverはそのBox単体のrevision/contentHash検証だけでなく、**適用時点のcurrent canonical Box graph** に対して参照整合性を検証する。

- parentBoxIdは同一Userのactive Boxであること
- self parentは禁止
- current graph上で対象Boxのdescendantをparentに指定してcycleを作る更新は禁止
- parentBoxId != null のとき locationId はnull
- parentBoxId == null のとき locationIdはBoxLocationまたはUNASSIGNED

複数端末がofflineで別々に親関係を編集した場合でも、serverで先にcommitされた変更を含むcurrent graphを使って後続operationを検証する。
例として端末1が `A.parent=B`、端末2が `B.parent=A` を送った場合、先に成立した一方だけがcommit可能で、後続側はcycleとして `REJECTED / BOX_PARENT_CYCLE` とする。

cycleは同一Boxのrevision conflictだけでは検出できないため、graph validationをBusiness transaction内で行う。
REJECTED時はOutboxを自動削除せず、利用者が収納先を修正できるblocked stateとして扱う。

Conflict `USE_LOCAL` でも同じcurrent graph validationを再実行する。stale revision確認を通過しても、適用時にcycle/reference違反となる場合は `RESOLUTION_REJECTED` とし、Conflict/Outboxを保持する。

Pull / Full Resyncでserver canonical graphを受け取る場合、clientはcycleのないserver stateを前提とする。ただしlocal Outbox reapplyでcycleが発生する場合、そのOutboxを破棄せずlocal blocked stateとして保持し、server canonical graphを破壊しない。

## 10. Pull API

### 10.1 Request
```text
GET /api/sync/pull?cursor=<syncSeq>&limit=<n>
```

- `cursor` は最後に**完全にadopt済み**のsyncSeq decimal string
- `cursor` 省略/nullは通常incremental Pullでは許可せず `FULL_RESYNC_REQUIRED`
- default limit = 200
- max limit = 500

### 10.2 Snapshot boundary
各Pull response開始時にUserに見える最新global syncSeqを `throughSeq` として固定し、そのresponseでは:
```text
cursor < syncSeq <= throughSeq
```
だけを対象にする。

paging中に新規変更が入っても次のresponse以降で取得する。

### 10.3 Response
```json
{
  "fromCursor": "850",
  "throughSeq": "950",
  "changes": [
    {
      "syncSeq": "851",
      "entityType": "ITEM",
      "entityId": "item-id",
      "revision": "7",
      "contentHash": "...",
      "deleted": false,
      "serverUpdatedAt": "...",
      "payload": {}
    }
  ],
  "nextCursor": "900",
  "hasMore": true
}
```

- changesはsyncSeq昇順
- 同一entityが範囲内で複数回変更されていてもchange eventを省略しない
- payloadはそのSyncChangeLog eventに対応するBusiness snapshotを返す必要がある
- tombstoneもpayloadを返す
- clientはresponse全体をlocal transactionでadoptし、成功後のみ `nextCursor` を保存
- `changes=[]` でも `nextCursor` は安全に進められるserver確定cursorを返せる

**重要:** current Business rowだけから過去event payloadを再構築すると、同一entityの複数revisionを正しく返せない。このためSyncChangeLogはPullに必要なcanonical Business payload snapshotを保持するか、同等にevent時点snapshotを取得できる構造を持つ。

## 11. Pull errors
- `400 INVALID_CURSOR`
- `401 AUTH_REQUIRED`
- `409 RESTORE_LOCKED` retryable
- `409 FULL_RESYNC_REQUIRED`: cursorがnull/retention外/認識不能
- `500 INTERNAL_ERROR`
- `503 TEMPORARILY_UNAVAILABLE` retryable

`FULL_RESYNC_REQUIRED` responseには現在の `latestSyncSeq` をdecimal stringで含めてよいが、clientはそれをincremental cursorとして直接採用しない。

## 12. Client cursor commit
Pull response処理:
1. local Businessへserver changeをadopt
2. pending Outbox対象entityならserver baseを反映した後、local pending Businessをreapply
3. 必要なlocal conflict stateを更新
4. `SyncState.pullCursor = nextCursor`
5. 同一Dexie transaction commit

途中失敗時はcursorを進めず、responseを再取得可能にする。

## 13. Error retry classification
retryable:
- `RESTORE_LOCKED`
- `TEMPORARILY_UNAVAILABLE`
- network/timeout

user/action required:
- `AUTH_REQUIRED`
- `FULL_RESYNC_REQUIRED`
- `CONFLICT`
- `REJECTED`

program/data error:
- `INVALID_REQUEST`
- `INVALID_CURSOR`
- `USER_SCOPE_VIOLATION`

retryable errorへclient Business/Outbox変更を加えない。

## 14. 現行APIとの差分
現行実装の以下はv0.8 targetではない。
- PullのISO timestamp `since`
- `updatedAt` order/cursor
- Pushの無条件Prisma upsert
- request全体 `{boxes,items,locations}`
- `{ok:true}` のみのPush response

v0.8では本書のrevision/contentHash/syncSeq契約へ置換する。

## 15. Blobを含む通常Sync sequence

通常syncのcanonical sequence:
```text
1. Pull
2. local Outbox reapply
3. Push候補をdependency順に選択
4. 各Push候補が参照する未confirmed photoをserver-ready化
5. Business Push
6. Push結果をlocalへ反映
7. final Pull
```

dependency順:
```text
BoxLocation → Box → Item
```

### 15.1 Pull
最初にserver canonical BusinessをPullし、Outboxがあるentityはserver baseをadopt後にpending local Businessをreapplyする。

この段階ではlocal photo Blobを削除しない。

### 15.2 Push candidateごとのphoto dependency
Business Push前に、そのcandidate payloadの `thumbs` が参照する各photoIdについてserver-readyを保証する。

```text
already CONFIRMED
  → upload不要

PENDING / retryable error
  → original upload
  → thumbnail upload
  → server validation/reference-ready confirmation
  → CONFIRMED

original/thumbnail不足または恒久validation error
  → Business Pushしない
```

Business payloadから削除済みのphotoは、そのPushのdependencyとしてuploadしない。

### 15.3 Blob-first boundary
server-ready confirmation前にBusiness referenceをcommitしない。

逆方向は許容する:
```text
blob confirmed
  ↓
Business Push失敗/CONFLICT
  ↓
blobはunreferenced
  ↓
30日GC candidate
```

したがってblob uploadとBusiness DB transactionを分散transactionとしてatomic化しない。orphan GCで補償する。

### 15.4 Upload failure
photo upload/confirmationが:
- network/timeout/5xx/RESTORE_LOCKED → retryable。candidate Outbox保持、次回retry
- AUTH_REQUIRED → sync停止、再認証待ち
- local original missing → photo recovery/user action required。Business Pushしない
- validation/hash/parent conflict → permanent photo errorとしてBusiness Pushしない

同一sync cycleでphoto dependencyが失敗しても、依存しない他entityのPushは継続可能。

### 15.5 Business Push result
- APPLIED / UNCHANGED → corresponding Outbox削除、server metadata採用
- CONFLICT → Outbox保持、SyncConflictへ
- REJECTED PHOTO_NOT_READY → photo stateを再確認し、blind retryしない
- request-level retryable error →対象Outbox保持

### 15.6 Final Pull
Push後は必ず可能な範囲でfinal Pullを行い、自端末PushによるSyncChangeLog eventと、sync中に他端末がcommitした変更をadoptする。

Pushが一部CONFLICT/REJECTEDでも、request-levelでPull不能でなければfinal Pullは実行する。

### 15.7 Sync cycle completion
sync cycleは全Outboxが空でなくても完了可能。

UI上は少なくとも:
- synced: Outbox/Conflict/retry待ちなし
- pending: 未Push/Blob retry待ちあり
- conflict: user resolution必要
- blocked: auth/Restore lock等

を区別する。

## 16. PhotoUploadStateとの境界
Sync設計では次の意味だけ要求する。
- `PENDING`: server-ready未確認
- `UPLOADING`: 現在upload/validation中
- `CONFIRMED`: original + required thumbnailがserver validation済みでBusiness reference可能

network failure時は `PENDING` に戻してretry可能。恒久errorの詳細はPhoto設計側で保持する。

`CONFIRMED` は「現在のUser scope serverでそのphotoId/photoHashがreference-ready」を意味し、単なるHTTP upload成功ではない。

## 17. SyncConflict resolution

### 17.1 基本方針
v0.8ではfield単位auto-mergeを行わない。利用者はentity単位で次の2択を行う。

- `KEEP_SERVER`: 現在のserver canonical版を採用
- `USE_LOCAL`: この端末のpending Business版をserverへ適用

Conflictは削除/復活を含むBusiness state全体を比較する。client/serverの `updatedAt` はwinner判定に使わない。

### 17.2 Conflict一覧API
`GET /api/sync/conflicts`

serverに存在する未解決SyncConflictをauthenticated User scopeで返す。

各item:
```json
{
  "conflictId": "...",
  "entityType": "ITEM",
  "entityId": "...",
  "clientBaseRevision": "4",
  "clientContentHash": "...",
  "clientPayload": {},
  "serverRevision": "5",
  "serverContentHash": "...",
  "serverPayload": {},
  "createdAt": "...",
  "updatedAt": "..."
}
```

local Outboxがさらに編集されている場合、UI表示時の「この端末」は**現在のlocal Outbox payload**を優先表示する。server Conflict内のclientPayloadは競合発生時snapshotとして扱う。

### 17.3 Resolve API
`POST /api/sync/conflicts/{conflictId}/resolve`

KEEP_SERVER:
```json
{
  "resolution": "KEEP_SERVER",
  "expectedServerRevision": "5"
}
```

USE_LOCAL:
```json
{
  "resolution": "USE_LOCAL",
  "expectedServerRevision": "5",
  "localContentHash": "...",
  "localPayload": {}
}
```

USE_LOCALは現在のlocal Outbox payloadを送る。競合発生時client snapshotへ巻き戻さない。

### 17.4 Stale check
resolve transaction開始時にcurrent server Business revision/contentHashを再読込する。

`expectedServerRevision != current server revision` の場合:
- resolutionを適用しない
- SyncConflictのserver snapshotをcurrentへ更新
- HTTP 409 `CONFLICT_STALE`
- responseに最新server revision/contentHash/payloadを返す
- clientは利用者へ最新比較を再表示し、再選択を要求

自動で同じresolutionを新revisionへ適用しない。

### 17.5 KEEP_SERVER
expected revisionがcurrentなら:
1. SyncConflict削除
2. server Businessは変更しない
3. server側に新しいsyncSeqは発行しない
4. responseにcurrent server canonical snapshotを返す

clientは同一local transactionで:
1. local Businessをserver snapshotへ置換
2. 対応Outbox削除
3. local SyncConflict削除

KEEP_SERVERはserver Business変更ではないためSyncChangeLog eventを追加しない。

### 17.6 USE_LOCAL
expected revisionがcurrentなら:
1. local payload validation
2. photo/reference dependency再検証
3. current server revisionをbaseとしてBusiness update
4. revision increment
5. contentHash/serverUpdatedAt/syncSeq更新
6. SyncChangeLog insert
7. SyncConflict削除
8. commit

response:
```json
{
  "status": "RESOLVED",
  "resolution": "USE_LOCAL",
  "revision": "6",
  "contentHash": "...",
  "syncSeq": "...",
  "serverUpdatedAt": "...",
  "payload": {}
}
```

clientはAPPLIEDと同様にserver metadataを採用しOutbox/SyncConflictを削除する。その後通常Pullで収束する。

### 17.7 USE_LOCAL validation failure
photo未ready、reference不存在、reserved/immutable violation等ではresolutionをcommitしない。

- HTTP 422 `RESOLUTION_REJECTED`
- field/error codeを返す
- SyncConflictとOutboxを保持
- 利用者がlocal Businessを修正後、再度resolve可能

### 17.8 Restore lock / auth
- `401 AUTH_REQUIRED`
- `409 RESTORE_LOCKED` retryable

lock中はresolutionを適用しない。

### 17.9 Conflict UI
通常画面を全面停止しない。sync statusからConflict一覧へ遷移できる。

一覧:
- entity type / display name
- 「サーバー側」と「この端末」の主要field差分
- deleted vs activeを明示
- photoはthumbnailと順序差を表示
- conflict発生時刻は参考表示のみ

detail:
- `サーバー側を採用`
- `この端末を採用`
- destructive結果（delete採用、写真/内容消失等）は確認dialogを追加

複数Conflictは1件ずつ解決可能。v0.8では一括「すべてlocal/server採用」は提供しない。

`CONFLICT_STALE` 時は「サーバー側が更新されました」と表示して最新比較へ差し替え、利用者に再選択を求める。

### 17.10 Local edit during conflict
Conflict中もlocal Business編集を許可し、Outbox payload/contentHashを最新状態へ更新する。

このためUSE_LOCALはresolve時点の最新Outboxを送る。

対象entityをlocalで再編集して結果がcurrent server contentHashと同一になった場合、次sync/resolveでUNCHANGED相当としてConflictを解消可能。

## 18. Full Resync

### 18.1 Purpose
Full Resyncは次の場合にlocal Business baseをserver canonicalへ再構築する。
- new local DB / `pullCursor=null`
- incremental cursorがSyncChangeLog retention外
- local reset後
- sync protocolが `FULL_RESYNC_REQUIRED` を返した場合

Outboxは失わない。

### 18.2 Snapshot creation
`POST /api/sync/full-resync/start`

serverはauthenticated User scopeで短いtransactionを実行する。

1. Restore lock状態を確認
2. current global `syncSeq` を `snapshotSeq` として固定
3. current canonical BoxLocation / Box / ItemをFullResyncSnapshotへcopy
4. `snapshotId` を発行
5. commit

response:
```json
{
  "snapshotId": "...",
  "snapshotSeq": "1200",
  "expiresAt": "...",
  "pageSizeDefault": 200,
  "pageSizeMax": 500
}
```

snapshotは作成後のBusiness更新から独立したimmutable read sourceとする。

current Business tableを複数requestで直接pageしない。そうすると取得途中のcreate/update/deleteにより1つの時点のsnapshotにならないため。

### 18.3 Server snapshot schema
FullResyncSnapshot:
```text
snapshotId       string
userId           string
snapshotSeq      int64
createdAt        timestamp
expiresAt        timestamp
status           ACTIVE | EXPIRED
```

FullResyncSnapshotEntity:
```text
snapshotId       string
entityType       BOX_LOCATION | BOX | ITEM
entityId         string
payload          object
revision         int64
contentHash      string
syncSeq          int64
serverUpdatedAt  timestamp
deleted          boolean
```

identity:
```text
(snapshotId, entityType, entityId)
```

index:
```text
(snapshotId, entityType, entityId)
```

snapshot entityはevent historyではなく、start transaction時点のcurrent canonical rowの固定copy。

### 18.4 Snapshot lifetime
v0.8ではFull Resync snapshot leaseを **60分** とする。

各page取得で延長しない。開始から60分でexpire可能。

理由:
- indefinitely retained snapshotを作らない
- mobile/browser中断をある程度許容
- 長時間中断後は最新server stateからやり直す方が安全

expired snapshotは `FULL_RESYNC_SNAPSHOT_EXPIRED`。clientはstagingを破棄して新しいstartからやり直す。Outboxは保持する。

### 18.5 Paging API
```text
GET /api/sync/full-resync/{snapshotId}/{entityType}?after=<entityId>&limit=<n>
```

entity type取得順:
```text
BOX_LOCATION → BOX → ITEM
```

- order = entityId ascending
- `after` は直前page最後のentityId。初回は省略
- default 200 / max 500
- offset pagingは使わない
- page responseの全recordは同じsnapshotId/snapshotSeqに属する

response:
```json
{
  "snapshotId": "...",
  "snapshotSeq": "1200",
  "entityType": "BOX",
  "records": [
    {
      "entityId": "...",
      "revision": "4",
      "contentHash": "...",
      "syncSeq": "1180",
      "serverUpdatedAt": "...",
      "deleted": false,
      "payload": {}
    }
  ],
  "nextAfter": "...",
  "hasMore": true
}
```

空のentity typeは `records=[]`, `hasMore=false`。

### 18.6 Local staging state
`fullResyncState`:
```text
id                "FULL_RESYNC"
snapshotId        string
snapshotSeq       int64
expiresAt         timestamp
phase             BOX_LOCATION | BOX | ITEM | READY_TO_ADOPT
boxLocationAfter  string?
boxAfter          string?
itemAfter         string?
boxLocationDone   boolean
boxDone           boolean
itemDone          boolean
startedAt         timestamp
updatedAt         timestamp
```

staging Business storesはserver Business schemaからuserIdを除いた同一recordを保持する。

各pageは:
1. response snapshotId/snapshotSeqをstateと照合
2. recordsを対応staging storeへupsert
3. nextAfter/doneを更新
4. 同一IndexedDB transactionでcommit

page commit失敗時はcursorを進めない。

### 18.7 Resume
browser reload等では、snapshotがexpiresAt前なら保存済みpage cursorからresume可能。

serverがsnapshot不存在/expiredを返した場合:
- staging stores + fullResyncStateだけを破棄
- current Business / Outbox / local photo blobは変更しない
- new snapshotをstart

### 18.8 Adopt boundary
3 entity typeすべてdoneかつ同じsnapshotId/snapshotSeqであることを確認後だけadoptする。

single IndexedDB transaction:
1. current BoxLocation / Box / Item storesをclear
2. staging BoxLocation → Box → Itemをcurrentへcopy
3. `SyncState.pullCursor=snapshotSeq`
4. `fullResyncAt` 更新
5. current server base adoption commit

**Outboxはこのtransactionで削除・変更しない。**

adopt成功後、別のlocal transaction群で保持Outboxを:
```text
BoxLocation → Box → Item
```
順にreapplyする。

Outbox reapply失敗時も `pullCursor=snapshotSeq` は有効であり、server snapshot adoptionをrollbackしない。対象Outboxを保持し、local recovery/errorとして扱う。

### 18.9 After adopt
Outbox reapply後:
1. photo dependenciesをserver-ready化
2. normal Push
3. incremental Pull from `snapshotSeq`

snapshot作成後にserverへ入った変更は `syncSeq > snapshotSeq` なので、このincremental Pullで回収する。

### 18.10 Tombstone / physical purge
Full Resync snapshotは**start時点でcurrent serverに存在するrowだけ**をcopyする。

既にphysical purge済みのtombstoneはsnapshotへ含めない。Full Resyncはlocal current Businessを全置換するため、そのentityはlocalから消える。

snapshot作成後にsource Business rowがphysical purgeされてもsnapshot copyは影響を受けない。

### 18.11 Error codes

## 20. In-flight local edit safety

Outboxはlocal-only `mutationId` を持つ。

- 利用者によるBusiness editごとにnew mutationId
- SyncのPull/rebase/reapplyだけではmutationIdを変更しない
- Push/Conflict resolve request送信時にcurrent mutationIdをcapture
- response処理時、OutboxのmutationIdがcapture値と一致する場合だけそのOutboxを削除可能

response待ち中に同entityが再編集されmutationIdが変わった場合:
- APPLIED/USE_LOCAL成功: newer Outboxを保持し、baseRevisionをresponseのserver revisionへrebaseして次回Push
- UNCHANGED: newer Outboxを保持し、server canonical baseへrebaseしてcurrent local payloadを再適用
- KEEP_SERVER成功: request送信後のnewer local editを勝手に削除しない。server snapshotをbaseとしてnewer Outboxをrebaseし、次回通常Sync対象とする
- CONFLICT/REJECTED: newer Outboxを保持し、current local payloadを失わない

これにより古いnetwork responseが新しいlocal editを削除することを禁止する。

SyncConflictは1 entityにつき最大1 unresolved rowとする。新しいconflictは同entity rowをcurrent conflict snapshotへ更新し、audit historyとして積み上げない。
