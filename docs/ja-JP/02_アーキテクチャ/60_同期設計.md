# Sync設計

## 1. 基本原則
server canonical stateとlocal offline BusinessをOutbox方式で収束させる。

通常sync:
```text
Pull → Outbox reapply → Push → Pull
```

Business updateとOutbox writeは同一IndexedDB transaction。

## 2. Push conflict
```text
baseRevision == server.revision
  → normal update

baseRevision != server.revision
  → contentHash same: UNCHANGED
  → contentHash different: CONFLICT
```

updatedAtの新旧でwinnerを決めない。

## 3. Pull
SyncChangeLogをcanonical sourceとし、DB-wide monotonic signed 64-bit `syncSeq` をcursorに使用する。User scopeで `syncSeq > cursor` を取得する。

SyncChangeLog retentionは90日。cursorが保持範囲外なら `FULL_RESYNC_REQUIRED`。

## 4. Tombstone
server accepted DELETE後30日を経過したtombstoneはphysical deletion可能。offline未Push deleteはlocalで保持する。

## 5. Full Resync
- fixed `snapshotSeq`
- entity typeごとにpaging
- stagingへ構築
- staging完成後のみadopt
- local Outboxを保持
- adopt後Outboxをreapply

Outbox reapply order:
```text
BoxLocation → Box → Item
```

## 6. SyncConflict
SyncConflictはaudit historyではなく未解決状態の一時領域。解決時にserver revisionを再確認し、staleなら最新server snapshotと再比較する。

## 7. Restore lock中
非owner device/sessionの以下をretryable `RESTORE_LOCKED`としてpauseする。
- Business Pull
- Business Push
- Business-related original/thumbnail upload
- server photo reference confirmation

local閲覧・Business編集は継続しOutboxへ記録する。unlock後は通常syncへ戻す。

## 8. Wire format共通規則
- endpointは `/api/sync/push`, `/api/sync/pull`
- authenticated Userはsession/tokenからserverが確定し、requestのuserIdを信用しない
- `revision`, `syncSeq`, cursor等のsigned 64-bit値はJSON **decimal string** で送受信する
- timestampはRFC3339
- entity typeは `BOX | ITEM | BOX_LOCATION`
- error responseはmachine-readable `code` を必須とする
- unknown fieldはv0.8ではvalidation errorとし、暗黙にBusiness contentへ取り込まない

## 9. Push API

### 9.1 Request
`POST /api/sync/push`

```json
{
  "operations": [
    {
      "operationId": "client-generated-id",
      "entityType": "BOX",
      "entityId": "box-id",
      "operation": "UPSERT",
      "baseRevision": "12",
      "contentHash": "sha256-hex",
      "payload": {}
    }
  ]
}
```

rules:
- `operationId` はrequest内unique。response対応付け用でBusiness identityではない
- `entityId` とpayload内identityがある場合は一致必須
- `operation` は `UPSERT | DELETE`
- DELETEもcanonical deleted Business payload/contentHashを送る
- request内operation順をserver commit順として保証しない
- clientはdependency順 `BoxLocation → Box → Item` で送る
- 1 request最大100 operations
- payload最大サイズは通常HTTP/API制限に従う。photo binaryは含めない

### 9.2 Per-operation processing
各operationは独立logical transaction。

```text
entity不存在 + baseRevision=0 + UPSERT
  → CREATE/APPLIED

entity不存在 + その他
  → NOT_FOUND または CONFLICT相当

entity存在 + baseRevision == server.revision
  → validate → APPLIED

entity存在 + baseRevision != server.revision
  + contentHash == server.contentHash
    → UNCHANGED
  + contentHash != server.contentHash
    → CONFLICT
```

Box.code immutable違反、reference不存在、photo未confirm等はAPPLIEDにしない。

### 9.3 Response
HTTP 200は「request envelopeを処理できた」を意味し、全operation成功を意味しない。

```json
{
  "results": [
    {
      "operationId": "client-generated-id",
      "entityType": "BOX",
      "entityId": "box-id",
      "status": "APPLIED",
      "revision": "13",
      "contentHash": "sha256-hex",
      "syncSeq": "901",
      "serverUpdatedAt": "2026-09-27T00:00:00.000Z"
    }
  ]
}
```

status:
- `APPLIED`: server Business変更commit済み。Outbox削除可能
- `UNCHANGED`: server canonical contentが同一。server metadataを採用しOutbox削除可能
- `CONFLICT`: SyncConflict作成/更新。Outboxは解決まで保持
- `REJECTED`: validation/reference/photo等の恒久的error。Outboxを自動削除しない

CONFLICT resultには:
```json
{
  "status": "CONFLICT",
  "conflictId": "...",
  "serverRevision": "13",
  "serverContentHash": "...",
  "serverPayload": {}
}
```
を含める。

REJECTED resultには `error.code`, `error.message`, optional `error.field` を含める。

### 9.4 Push request-level errors
request-level errorはoperationを処理開始できない場合。

- `400 INVALID_REQUEST`
- `401 AUTH_REQUIRED`
- `403 USER_SCOPE_VIOLATION`
- `409 RESTORE_LOCKED` retryable
- `413 REQUEST_TOO_LARGE`
- `500 INTERNAL_ERROR`
- `503 TEMPORARILY_UNAVAILABLE` retryable

request-level failureではclientはそのrequestのOutboxを削除しない。

### 9.5 REJECTED codes
最低限:
- `VALIDATION_ERROR`
- `ENTITY_NOT_FOUND`
- `REFERENCE_NOT_FOUND`
- `RESERVED_ENTITY`
- `IMMUTABLE_FIELD`
- `BOX_CODE_CONFLICT`
- `PHOTO_NOT_READY`
- `PHOTO_PARENT_CONFLICT`

## 10. Pull API

### 10.1 Request
```text
GET /api/sync/pull?cursor=<syncSeq>&limit=<n>
```

- `cursor` は最後に**完全にadopt済み**のsyncSeq decimal string
- `cursor` 省略/nullは通常incremental Pullでは許可せず `FULL_RESYNC_REQUIRED`
- default limit = 200
- max limit = 500

### 10.2 Snapshot boundary
各Pull response開始時にUserに見える最新global syncSeqを `throughSeq` として固定し、そのresponseでは:
```text
cursor < syncSeq <= throughSeq
```
だけを対象にする。

paging中に新規変更が入っても次のresponse以降で取得する。

### 10.3 Response
```json
{
  "fromCursor": "850",
  "throughSeq": "950",
  "changes": [
    {
      "syncSeq": "851",
      "entityType": "ITEM",
      "entityId": "item-id",
      "revision": "7",
      "contentHash": "...",
      "deleted": false,
      "serverUpdatedAt": "...",
      "payload": {}
    }
  ],
  "nextCursor": "900",
  "hasMore": true
}
```

- changesはsyncSeq昇順
- 同一entityが範囲内で複数回変更されていてもchange eventを省略しない
- payloadはそのSyncChangeLog eventに対応するBusiness snapshotを返す必要がある
- tombstoneもpayloadを返す
- clientはresponse全体をlocal transactionでadoptし、成功後のみ `nextCursor` を保存
- `changes=[]` でも `nextCursor` は安全に進められるserver確定cursorを返せる

**重要:** current Business rowだけから過去event payloadを再構築すると、同一entityの複数revisionを正しく返せない。このためSyncChangeLogはPullに必要なcanonical Business payload snapshotを保持するか、同等にevent時点snapshotを取得できる構造を持つ。

## 11. Pull errors
- `400 INVALID_CURSOR`
- `401 AUTH_REQUIRED`
- `409 RESTORE_LOCKED` retryable
- `409 FULL_RESYNC_REQUIRED`: cursorがnull/retention外/認識不能
- `500 INTERNAL_ERROR`
- `503 TEMPORARILY_UNAVAILABLE` retryable

`FULL_RESYNC_REQUIRED` responseには現在の `latestSyncSeq` をdecimal stringで含めてよいが、clientはそれをincremental cursorとして直接採用しない。

## 12. Client cursor commit
Pull response処理:
1. local Businessへserver changeをadopt
2. pending Outbox対象entityならserver baseを反映した後、local pending Businessをreapply
3. 必要なlocal conflict stateを更新
4. `SyncState.pullCursor = nextCursor`
5. 同一Dexie transaction commit

途中失敗時はcursorを進めず、responseを再取得可能にする。

## 13. Error retry classification
retryable:
- `RESTORE_LOCKED`
- `TEMPORARILY_UNAVAILABLE`
- network/timeout

user/action required:
- `AUTH_REQUIRED`
- `FULL_RESYNC_REQUIRED`
- `CONFLICT`
- `REJECTED`

program/data error:
- `INVALID_REQUEST`
- `INVALID_CURSOR`
- `USER_SCOPE_VIOLATION`

retryable errorへclient Business/Outbox変更を加えない。

## 14. 現行APIとの差分
現行実装の以下はv0.8 targetではない。
- PullのISO timestamp `since`
- `updatedAt` order/cursor
- Pushの無条件Prisma upsert
- request全体 `{boxes,items,locations}`
- `{ok:true}` のみのPush response

v0.8では本書のrevision/contentHash/syncSeq契約へ置換する。

## 15. Blobを含む通常Sync sequence

通常syncのcanonical sequence:
```text
1. Pull
2. local Outbox reapply
3. Push候補をdependency順に選択
4. 各Push候補が参照する未confirmed photoをserver-ready化
5. Business Push
6. Push結果をlocalへ反映
7. final Pull
```

dependency順:
```text
BoxLocation → Box → Item
```

### 15.1 Pull
最初にserver canonical BusinessをPullし、Outboxがあるentityはserver baseをadopt後にpending local Businessをreapplyする。

この段階ではlocal photo Blobを削除しない。

### 15.2 Push candidateごとのphoto dependency
Business Push前に、そのcandidate payloadの `thumbs` が参照する各photoIdについてserver-readyを保証する。

```text
already CONFIRMED
  → upload不要

PENDING / retryable error
  → original upload
  → thumbnail upload
  → server validation/reference-ready confirmation
  → CONFIRMED

original/thumbnail不足または恒久validation error
  → Business Pushしない
```

Business payloadから削除済みのphotoは、そのPushのdependencyとしてuploadしない。

### 15.3 Blob-first boundary
server-ready confirmation前にBusiness referenceをcommitしない。

逆方向は許容する:
```text
blob confirmed
  ↓
Business Push失敗/CONFLICT
  ↓
blobはunreferenced
  ↓
30日GC candidate
```

したがってblob uploadとBusiness DB transactionを分散transactionとしてatomic化しない。orphan GCで補償する。

### 15.4 Upload failure
photo upload/confirmationが:
- network/timeout/5xx/RESTORE_LOCKED → retryable。candidate Outbox保持、次回retry
- AUTH_REQUIRED → sync停止、再認証待ち
- local original missing → photo recovery/user action required。Business Pushしない
- validation/hash/parent conflict → permanent photo errorとしてBusiness Pushしない

同一sync cycleでphoto dependencyが失敗しても、依存しない他entityのPushは継続可能。

### 15.5 Business Push result
- APPLIED / UNCHANGED → corresponding Outbox削除、server metadata採用
- CONFLICT → Outbox保持、SyncConflictへ
- REJECTED PHOTO_NOT_READY → photo stateを再確認し、blind retryしない
- request-level retryable error →対象Outbox保持

### 15.6 Final Pull
Push後は必ず可能な範囲でfinal Pullを行い、自端末PushによるSyncChangeLog eventと、sync中に他端末がcommitした変更をadoptする。

Pushが一部CONFLICT/REJECTEDでも、request-levelでPull不能でなければfinal Pullは実行する。

### 15.7 Sync cycle completion
sync cycleは全Outboxが空でなくても完了可能。

UI上は少なくとも:
- synced: Outbox/Conflict/retry待ちなし
- pending: 未Push/Blob retry待ちあり
- conflict: user resolution必要
- blocked: auth/Restore lock等

を区別する。

## 16. PhotoUploadStateとの境界
Sync設計では次の意味だけ要求する。
- `PENDING`: server-ready未確認
- `UPLOADING`: 現在upload/validation中
- `CONFIRMED`: original + required thumbnailがserver validation済みでBusiness reference可能

network failure時は `PENDING` に戻してretry可能。恒久errorの詳細はPhoto設計側で保持する。

`CONFIRMED` は「現在のUser scope serverでそのphotoId/photoHashがreference-ready」を意味し、単なるHTTP upload成功ではない。

## 17. 設計残件
- SyncConflict resolution API/UI
- Full Resync paging/staging schema

`RESTORE_LOCKED` とnormal blob upload sequenceは通常sync protocolへ統合済み。
