# 認証フロー（通常ログイン + TOTP + ログアウト）

本書では、認証 API がどのように連携してログイン状態を確立するかを  
「シーケンス（API 呼び出し順）」「User モデルの状態遷移」の2軸で整理する。

---

# 1. 通常ログインフロー（TOTP 無効ユーザー）

## 1.1 シーケンス

1. `/api/auth/login` に email/password を送信  
2. 認証成功  
3. セッション Cookie を発行  
4. クライアントは Cookie を保持した状態で各 API を利用

## 1.2 成功レスポンス例

```json
{
  "ok": true,
  "user": {
    "id": "xxx",
    "displayName": "..."
  }
}
```

---

# 2. TOTP 必須ユーザーのログインフロー（2段階）

## 2.1 シーケンス

1. `/api/auth/login`
   - email/password 正しい
   - **totpEnabled = true**
   - セッションは発行されず `loginId` が返る

2. `/login/totp` 画面に遷移（UI）

3. `/api/auth/login/totp`
   - loginId + 6 桁コードを送信  
   - 認証成功時に **初めてセッションを発行**

## 2.2 User 状態の利用フィールド

| フィールド | 用途 |
|-----------|------|
| totpEnabled | TOTP が有効か |
| totpFailCount | 連続失敗回数 |
| lockUntil | ロックされているか |
| totpSecretEnc | 秘密鍵（暗号化） |

---

# 3. TOTP セットアップフロー（新規登録 or 再設定）

## 3.1 シーケンス

1. `/api/auth/totp/setup`  
   - 一時秘密鍵（pending）が発行され、QR コードを返す  
   - User の `totpPendingSecretEnc` / `totpPendingAt` がセットされる

2. `/api/auth/totp/verify`  
   - 6 桁コードで検証  
   - 成功時：
     - `totpPendingSecretEnc` → `totpSecretEnc` に移動  
     - `totpEnabled = true` に更新  
     - `recoveryCodes` 発行（任意）

3. `/api/auth/totp/status`  
   - 現在の TOTP 状態（enabled / pending / disabled）を確認できる

4. `/api/auth/totp/disable`  
   - `totpEnabled = false`  
   - `totpSecretEnc = null`

---

# 4. ログアウトフロー

1. `/api/auth/logout` を実行  
2. 対象の SyncToken レコードを削除  
3. セッション Cookie 無効化

---

# 5. 状態遷移（User モデルの動き）

## 5.1 TOTP 状態遷移

| 状態 | 条件 | 遷移先 |
|------|------|---------|
| disabled | 初期状態 | setup 実行 → pending |
| pending | setup 済みだが verify していない | verify 成功 → enabled |
| enabled | TOTP 有効 | disable 実行 → disabled |

### pending → enabled で書き換わるフィールド

| フィールド | 値 |
|-----------|-------------|
| totpPendingSecretEnc | null |
| totpPendingAt | null |
| totpSecretEnc | 一時鍵が移動 |
| totpEnabled | true |

---

# 6. 開発者向け補足

- dev mode では `devtoken` による即ログインが可能  
- 本番では Cookie ベースのセッションが必須  
- loginId は TOTP 用の短期レコードとして扱う（数分で失効推奨）
