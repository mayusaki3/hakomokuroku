# 認証フロー（User登録 + 通常ログイン + TOTP + ログアウト）

本書では、認証 API がどのように連携してログイン状態を確立するかを  
「シーケンス（API 呼び出し順）」「User モデルの状態遷移」の2軸で整理する。

---

# 0. v0.8 scope / boundary

v0.8では以下を認証必須機能として維持する。

- User新規登録
- ID/email + passwordによる通常Login
- TOTP login
- TOTP setup / verify / status / disable
- recovery code再発行
- Logout

server APIのUser scopeはauthenticated sessionから決定し、client指定userIdを認可根拠にしない。
認証sessionとBox.code発行用のDevice / DevicePrefix / local DeviceStateは別概念である。旧SyncTokenのdevice labelを新Device identityへ流用しない。

# 0.1 User registration

新規登録成功後にauthenticated sessionを確立し、そのUser専用local DB `hk-local-v2-<User.id>` をopen/createする。online初回利用ではFull Resync（新規Userならempty snapshotを含む）とDevice setupを行う。

TOTPは登録そのものの必須条件にはしない。登録後に利用者がMFA設定から有効化できる。

# 1. 通常ログインフロー（TOTP 無効ユーザー）

## 1.1 シーケンス

1. `/api/auth/login` に email/password を送信  
2. 認証成功  
3. セッション Cookie を発行  
4. クライアントは Cookie を保持した状態で各 API を利用

## 1.2 成功レスポンス例

```json
{
  "ok": true,
  "user": {
    "id": "xxx",
    "displayName": "..."
  }
}
```

---

# 2. TOTP 必須ユーザーのログインフロー（2段階）

## 2.1 シーケンス

1. `/api/auth/login`
   - email/password 正しい
   - **totpEnabled = true**
   - セッションは発行されず `loginId` が返る

2. `/login/totp` 画面に遷移（UI）

3. `/api/auth/login/totp`
   - loginId + 6 桁コードを送信  
   - 認証成功時に **初めてセッションを発行**

## 2.2 User 状態の利用フィールド

| フィールド | 用途 |
|-----------|------|
| totpEnabled | TOTP が有効か |
| totpFailCount | 連続失敗回数 |
| lockUntil | ロックされているか |
| totpSecretEnc | 秘密鍵（暗号化） |

---

# 3. TOTP セットアップフロー（新規登録 or 再設定）

## 3.1 シーケンス

1. `/api/auth/totp/setup`  
   - 一時秘密鍵（pending）が発行され、QR コードを返す  
   - User の `totpPendingSecretEnc` / `totpPendingAt` がセットされる

2. `/api/auth/totp/verify`  
   - 6 桁コードで検証  
   - 成功時：
     - `totpPendingSecretEnc` → `totpSecretEnc` に移動  
     - `totpEnabled = true` に更新  
     - `recoveryCodes` 発行（任意）

3. `/api/auth/totp/status`  
   - 現在の TOTP 状態（enabled / pending / disabled）を確認できる

4. `/api/auth/totp/disable`  
   - `totpEnabled = false`  
   - `totpSecretEnc = null`

---

# 4. ログアウトフロー

1. `/api/auth/logout` を実行  
2. server sessionを無効化
3. セッション Cookieを無効化
4. current Userのlocal session bindingを解除する
5. local Business / Outbox / photo / DeviceStateは削除しない

---

# 5. 状態遷移（User モデルの動き）

## 5.1 TOTP 状態遷移

| 状態 | 条件 | 遷移先 |
|------|------|---------|
| disabled | 初期状態 | setup 実行 → pending |
| pending | setup 済みだが verify していない | verify 成功 → enabled |
| enabled | TOTP 有効 | disable 実行 → disabled |

### pending → enabled で書き換わるフィールド

| フィールド | 値 |
|-----------|-------------|
| totpPendingSecretEnc | null |
| totpPendingAt | null |
| totpSecretEnc | 一時鍵が移動 |
| totpEnabled | true |

---

# 6. 開発者向け補足

- dev modeの認証bypassを用意する場合もproduction build/runtimeで有効化しない。  
- 本番では Cookie ベースのセッションが必須  
- loginId はTOTP用の短期challengeとして扱い、短時間で失効させる
- TOTP secret/recovery codeはBusiness backup/IndexedDBへ含めない
- TOTP login完了前にauthenticated Business APIを利用可能にしない
