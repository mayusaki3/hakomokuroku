# 認証フロー（User登録 + 通常ログイン + TOTP + ログアウト）

本書では、認証 API がどのように連携してログイン状態を確立するかを  
「シーケンス（API 呼び出し順）」「User モデルの状態遷移」の2軸で整理する。

---

# 0. v0.8 scope / boundary

v0.8では以下を認証必須機能として維持する。

- User新規登録
- User ID + passwordによる通常Login
- TOTP login
- TOTP setup / verify / status / disable
- recovery code再発行
- Logout

server APIのUser scopeはauthenticated sessionから決定し、client指定userIdを認可根拠にしない。
認証sessionとBox.code発行用のDevice / DevicePrefix / local DeviceStateは別概念である。旧SyncTokenのdevice labelを新Device identityへ流用しない。

# 0.1 User registration

新規登録は未認証状態で行い、登録成功だけではauthenticated sessionを確立しない。利用者はログイン処理（User ID + password、TOTP有効時はTOTP）を完了した後、そのUser専用local DB `hk-local-v2-<User.id>` をopen/createする。online初回利用ではFull Resync（新規Userならempty snapshotを含む）とDevice setupを行う。UIはログイン画面を入口とし、「新規登録へ」から登録画面へ遷移する。

TOTPは登録そのものの必須条件にはしない。登録後に利用者がMFA設定から有効化できる。

# 1. 通常ログインフロー（TOTP 無効ユーザー）

## 1.1 シーケンス

1. `/api/auth/login` に User ID/password を送信  
2. 認証成功  
3. セッション Cookie を発行  
4. クライアントは Cookie を保持した状態で各 API を利用

## 1.2 成功レスポンス例

```json
{
  "ok": true,
  "user": {
    "id": "xxx",
    "displayName": "..."
  }
}
```

---

# 2. TOTP 必須ユーザーのログインフロー（2段階）

## 2.1 シーケンス

1. `/api/auth/login`
   - User ID/password 正しい
   - **totpEnabled = true**
   - セッションは発行されず `loginId` が返る

2. `/login/totp` 画面に遷移（UI）

3. `/api/auth/login/totp`
   - loginId + 6 桁コードを送信  
   - 認証成功時に **初めてセッションを発行**

## 2.2 User 状態の利用フィールド

| フィールド | 用途 |
|-----------|------|
| totpEnabled | TOTP が有効か |
| totpFailCount | 連続失敗回数 |
| lockUntil | ロックされているか |
| totpSecretEnc | 秘密鍵（暗号化） |

---

# 3. TOTP セットアップフロー（新規登録 or 再設定）

## 3.1 シーケンス

1. `/api/auth/totp/setup`  
   - 一時秘密鍵（pending）が発行され、QR コードを返す  
   - User の `totpPendingSecretEnc` / `totpPendingAt` がセットされる

2. `/api/auth/totp/verify`  
   - 6 桁コードで検証  
   - 成功時：
     - `totpPendingSecretEnc` → `totpSecretEnc` に移動  
     - `totpEnabled = true` に更新  
     - `recoveryCodes` 発行（任意）

3. `/api/auth/totp/status`  
   - 現在の TOTP 状態（enabled / pending / disabled）を確認できる

4. `/api/auth/totp/disable`  
   - `totpEnabled = false`  
   - `totpSecretEnc = null`

---


# 3.1 Recovery Code / Emergency Recovery

TOTP端末を利用できない場合、メール/SMSを必須インフラにせずRecovery Codeを標準復旧手段とする。

1. TOTP有効化時に複数のRecovery Codeを一度だけ表示し、利用者に安全な保管を求める。
2. Recovery Codeは1回限り使用可能とし、serverには平文を保存せず検証可能なhashのみ保持する。
3. Recovery Codeで認証した場合はTOTP再設定を案内する。
4. Recovery Codeも失った場合の最終手段として、server管理者向けCLIからEmergency Recovery Codeを発行できる。
5. Emergency Recovery Codeは対象User IDを明示確認して発行し、1回限り・短時間有効・serverにはhashのみ保持する。
6. Emergency Recovery Codeだけでは認証を完了できず、利用者本人のpasswordも必要とする。
7. CLIはUser passwordやTOTP secretを表示・変更しない。
8. Emergency Recovery成功後はTOTP再設定を必須導線として提示する。
9. メール認証コードは将来のoptional providerとし、v0.8の必須機能・必須User属性にしない。

復旧優先順位は次の通り。

```
TOTP
  ↓ 利用不可
Recovery Code
  ↓ 紛失/枯渇
server admin CLI → Emergency Recovery Code
  ↓
User password + Emergency Recovery Code
  ↓
Login → TOTP再設定
```

# 4. ログアウトフロー

1. `/api/auth/logout` を実行  
2. server sessionを無効化
3. セッション Cookieを無効化
4. current Userのlocal session bindingを解除する
5. local Business / Outbox / photo / DeviceStateは削除しない

---

# 5. 状態遷移（User モデルの動き）

## 5.1 TOTP 状態遷移

| 状態 | 条件 | 遷移先 |
|------|------|---------|
| disabled | 初期状態 | setup 実行 → pending |
| pending | setup 済みだが verify していない | verify 成功 → enabled |
| enabled | TOTP 有効 | disable 実行 → disabled |

### pending → enabled で書き換わるフィールド

| フィールド | 値 |
|-----------|-------------|
| totpPendingSecretEnc | null |
| totpPendingAt | null |
| totpSecretEnc | 一時鍵が移動 |
| totpEnabled | true |

---

# 6. 開発者向け補足

- dev modeの認証bypassを用意する場合もproduction build/runtimeで有効化しない。  
- 本番では Cookie ベースのセッションが必須  
- loginId はTOTP用の短期challengeとして扱い、短時間で失効させる
- TOTP secret/recovery codeはBusiness backup/IndexedDBへ含めない
- TOTP login完了前にauthenticated Business APIを利用可能にしない


# 7. User profile / session management

v0.8では旧版のUser profile機能を維持する。

- User nameの表示・編集
- User iconの表示・camera/file選択・回転・保存
- default icon fallback
- profile変更後のheader等への反映

User profileはserver User account metadataであり、Box / Item / BoxLocation Business Backupへ含めない。
offline中にserver profileを変更したことにしてOutboxへ積まない。profile変更はonline/authenticated operationとする。

認証session管理もv0.8で維持する。
利用者は現在のsession以外を含むログインsession一覧を確認し、個別失効または他sessionの一括失効を行える。
session失効は認証credentialだけに作用し、Device / DevicePrefix / local DeviceState、Business、Outbox、photoを削除しない。

「Box.code発行端末」と「ログインsession」は1:1とは限らず、UI上も別項目として扱う。
