# API 層設計（認証編）

本ドキュメントは API 層のうち、認証に関係する部分の責務と構造を整理する。

---

## 1. 認証 API の責務

認証に関係する API は以下の責務を持つ：

- クライアントからの資格情報の検証（メールアドレス・パスワード）
- セッションの生成・検証・破棄
- ログイン中ユーザーの基本情報の取得・更新

認証は **Cookie ベースのセッション** を使用し、API はすべて stateless に処理される。

---

## 2. 主要エンドポイント一覧

| エンドポイント | メソッド | 説明 |
|----------------|-----------|------|
| `/api/auth/login` | POST | 資格情報を検証し、セッション cookie を発行 |
| `/api/auth/me` | GET | 現在のセッション情報を返す |
| `/api/auth/logout` | POST | セッション cookie の破棄 |
| `/api/settings/user` | GET / PUT | ログインユーザーのプロフィール取得/更新 |

これらは UI 側 `authClient` および `server/auth.ts` に依存する。

---

## 3. セッション処理の方針

### 3-1. readSession

- Cookie を読み取り、セッション ID を Prisma から検証。
- 例外発生時は API 側で握りつぶすことを推奨（実装準拠）。
- `/api/auth/me` は例外時でも `200 + ok:false` を返す（既存テスト準拠）。

### 3-2. requireUserId

ログイン必須 API で使用するヘルパー。

- セッションがない場合 → `401 Unauthorized`
- セッションがあるが無効 → `401 Unauthorized`

---

## 4. クライアント側処理（概要）

### 4-1. ログインフロー

1. `/api/auth/login` へ POST  
2. 成功時、Cookie にセッションが設定される  
3. UI は `/api/auth/me` を呼び、ユーザー情報を取得  
4. プロフィール情報・MFA 状態などをローカルに保持  

### 4-2. ログアウト

- `/api/auth/logout` 実行後、UI はセッションを破棄し、ログインページへリダイレクト。

---

## 5. エラー処理方針

- パラメータ不正 → 400
- 認証失敗 → 401
- 内部例外 → 500（ただし `/api/auth/me` は 200 + ok:false）
- メッセージの過度な詳細化は禁止（セキュリティ方針）
