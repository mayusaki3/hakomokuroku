# Data Model設計

## 1. Identity / User boundary
Business identityは `(userId, id)`。異なるUserは同じ `id` を持てる。

serverはpayloadのuserIdを信用せずauthenticated Userからscopeを決定する。DB上のBusiness entityも `(userId,id)` を複合identityとし、entity間参照は `userId` を含む複合FKでcross-user referenceを防止する。

## 2. 共通型
- `id`: string。client生成。reserved entityのみ `UNASSIGNED`
- timestamp: RFC3339/ISO8601 offset入力、server保存はUTC milliseconds
- `revision`: signed 64-bit integer。local新規=0、server初回受理=1
- `syncSeq`: signed 64-bit integer
- `contentHash`: SHA-256 hex
- `thumbs`: ordered PhotoRef array。0〜10
- `tags`: orderedではないstring array。canonicalization時にsort

## 3. Business entity schema

### 3.1 Box
```text
userId           string      PK(1), FK -> User.id
id               string      PK(2)
code             string      required, immutable
name             string      required
locationId       string      required
tags             string[]    required, default []
note             string?     optional
thumbs           PhotoRef[]  required, default []
meta             object?     optional
createdAt        timestamp   required
updatedAt        timestamp   required
deletedAt        timestamp?  optional
serverUpdatedAt  timestamp?  null until first server acceptance
revision         int64       required, local default 0
contentHash      string      required
syncSeq          int64?      null until first server acceptance
```

constraints:
- PK `(userId,id)`
- UNIQUE `(userId,code)`
- FK `(userId,locationId) -> BoxLocation(userId,id)`
- `code` はcanonical Box.codeまたはreserved Boxの `UNASSIGNED`
- normal Boxの `id/code` は作成後immutable
- reserved `id=UNASSIGNED, code=UNASSIGNED` は通常編集/削除不可

### 3.2 Item
```text
userId           string      PK(1), FK -> User.id
id               string      PK(2)
boxId            string      required
name             string      required
tags             string[]    required, default []
note             string?     optional
thumbs           PhotoRef[]  required, default []
meta             object?     optional
createdAt        timestamp   required
updatedAt        timestamp   required
deletedAt        timestamp?  optional
serverUpdatedAt  timestamp?  null until first server acceptance
revision         int64       required, local default 0
contentHash      string      required
syncSeq          int64?      null until first server acceptance
```

constraints:
- PK `(userId,id)`
- FK `(userId,boxId) -> Box(userId,id)`
- `boxId` はnull/empty不可。箱外は `UNASSIGNED`

### 3.3 BoxLocation
```text
userId           string      PK(1), FK -> User.id
id               string      PK(2)
name             string      required
note             string?     optional
thumbs           PhotoRef[]  required, default []
meta             object?     optional
createdAt        timestamp   required
updatedAt        timestamp   required
deletedAt        timestamp?  optional
serverUpdatedAt  timestamp?  null until first server acceptance
revision         int64       required, local default 0
contentHash      string      required
syncSeq          int64?      null until first server acceptance
```

constraints:
- PK `(userId,id)`
- active nameはUser scope unique
- reserved `id=UNASSIGNED, name=UNASSIGNED` は通常編集/削除不可
- BoxLocationはBoxを参照しない

## 4. PhotoRef
Photoは独立Business sync entityではなく親entityのbusiness content。

```text
photoId    string  required
photoHash  string  required
```

配列順序が表示順。1 photoIdはexactly 1 Business parentに所属する。thumbnail bytesやupload stateはPhotoRefへ含めない。

## 5. contentHash business schema
hash対象は以下。

Box:
```text
code, name, locationId, tags, note, thumbs, meta, deleted
```

Item:
```text
boxId, name, tags, note, thumbs, meta, deleted
```

BoxLocation:
```text
name, note, thumbs, meta, deleted
```

`deleted` はboolean canonical stateであり `deletedAt` の時刻値はhashしない。

除外:
- userId / id
- createdAt / updatedAt / deletedAt timestamp / serverUpdatedAt
- revision / syncSeq / contentHash

canonicalization:
- optional string: trim + NFC、semantic no-valueはnull
- required display string: trim + NFC、emptyはvalidation error
- tags: trim + NFC、empty除去、exact dedupe、case-sensitive、deterministic sort
- thumbs: orderを維持
- object key順は固定
- canonical JSONをSHA-256

## 6. Delete transaction
- Item delete: Item tombstone
- Box delete: active child Itemの `boxId=UNASSIGNED` 更新 + Box tombstone
- BoxLocation delete: active child Boxの `locationId=UNASSIGNED` 更新 + BoxLocation tombstone

親deleteと全child correction、それぞれのmetadata更新、syncSeq採番、SyncChangeLog追加は同一server transaction。

## 7. BoxLocation name collision
**現行方針として採用する。**

active `BoxLocation.name` はUser scope unique。新規/renameをserverが受理するとき同名active recordが存在する場合、今回受理するrecordが要求名を取得し、既存recordを `name(n)` へ自動renameする。

- `n` は1からの最小未使用正整数
- server受理順を「後」とする
- client `updatedAt` は使用しない
- new/renamed recordと既存record auto-renameを同一transaction
- auto-renamed側も通常Business updateとしてrevision/contentHash/serverUpdatedAt/syncSeq/SyncChangeLogを更新
- reserved name `UNASSIGNED` はnormal recordへ使用不可

## 8. Local Outbox
同一entityの未同期変更は原則1行へ集約する。

```text
entityType     BOX | ITEM | BOX_LOCATION
entityId       string
operation      UPSERT | DELETE
baseRevision   int64
contentHash    string
payload        canonical Business payload
createdAt      timestamp
```

local DB自体がUser専用 `hk-local-v2-<User.id>` のためOutboxにuserIdは持たない。

identity:
- PK `(entityType,entityId)`

rules:
- Business update + Outbox upsertは同一IndexedDB transaction
- 再編集時も最初の `baseRevision` を維持
- payload/contentHash/operationは最新Business stateへ更新
- Push成功/競合解決成功まで時間削除しない

## 9. Local SyncState
User-local DBに1 record。

```text
id             "SYNC"
pullCursor     int64?
lastPullAt     timestamp?
lastPushAt     timestamp?
fullResyncAt   timestamp?
```

`pullCursor=null` はserver historyを安全に継続できるcursorが無い状態。新規DBはFull Resyncを要求する。

時刻fieldは表示/診断用でsync correctnessには使わない。

## 10. Server SyncChangeLog
```text
syncSeq          int64       PK
userId           string      required
entityType       BOX | ITEM | BOX_LOCATION
entityId         string      required
revision         int64       required
contentHash      string      required
deleted          boolean     required
serverUpdatedAt  timestamp   required
```

- `syncSeq` はDB-wide monotonic
- Business updateと同一transactionでinsert
- Pull payload本体はcurrent Business entityから取得してよいが、変更検出/cursorの正本はSyncChangeLog
- retention 90日
- index `(userId,syncSeq)`

## 11. Server SyncConflict
```text
id                        string      PK
userId                    string      required
entityType                 BOX | ITEM | BOX_LOCATION
entityId                   string      required
clientBaseRevision         int64       required
clientContentHash          string      required
clientPayload              object      required
serverRevisionAtConflict   int64       required
serverContentHashAtConflict string      required
serverPayloadAtConflict    object      required
createdAt                  timestamp   required
updatedAt                  timestamp   required
```

UNIQUE:
```text
(userId, entityType, entityId, clientBaseRevision, clientContentHash)
```

SyncConflictは未解決状態でありaudit historyではない。stale時は同じ行のserver snapshotを最新化する。

## 12. Restore auxiliary schema
### RestoreLock
```text
userId       string      PK
lockTokenHash string     required
expiresAt    timestamp   required
createdAt    timestamp   required
renewedAt    timestamp   required
```

raw lockTokenは保存しない。server clockでexpiry判定。

### RestoreApplyResult
```text
userId         string      PK(1)
applyId        string      PK(2)
requestDigest  string      required
status         COMMITTED   required
committedAt    timestamp   required
```

- same User + applyId idempotency
- requestDigestはsame applyId/different request検出専用
- commitから7日保持

### Local RestoreApplyMarker
```text
applyId  string  PK
```

## 13. Full Resync staging
Full Resync stagingはBusiness entityと同じbusiness/server metadata schemaを一時領域に保持する。

必要なcontrol state:
```text
snapshotSeq
entityType
pageCursor
completed
```

全entity typeのsnapshot取得完了後だけcurrent Businessへadoptする。Outboxはstagingへ含めず保持し、adopt後に再適用する。

## 14. 現行Prismaとの差分
現行 `apps/web/prisma/schema.prisma` はv0.8 target schemaではない。

主要差分:
- Box / Item / BoxLocationの `id` がglobal PK → `(userId,id)` identityへ変更
- Boxに `locationId` がなく自由文字列 `location` → BoxLocation FKへ変更
- BoxLocationが `boxId @unique` のBox従属 → independent flat masterへ変更
- sync metadata不足
- Outbox / SyncChangeLog / SyncConflict / Restore auxiliary model不足
- Vision fieldsはv1.0対象。v0.8 Business schema/hash対象から除外

## 15. Server DB constraints

v0.8のserver DBは現行構成を踏襲し **SQLite + Prisma** を対象とする。DBで保証できる不変条件とservice transactionで保証する業務条件を分離する。

### 15.1 DB-level key / unique / FK

Box:
- PRIMARY KEY / Prisma compound id: `(userId,id)`
- UNIQUE: `(userId,code)`
- FK: `userId -> User.id ON DELETE CASCADE`
- FK: `(userId,locationId) -> BoxLocation(userId,id)`
- INDEX: `(userId,serverUpdatedAt)`
- INDEX: `(userId,syncSeq)`
- INDEX: `(userId,locationId,deletedAt)`

Item:
- PRIMARY KEY / compound id: `(userId,id)`
- FK: `userId -> User.id ON DELETE CASCADE`
- FK: `(userId,boxId) -> Box(userId,id)`
- INDEX: `(userId,serverUpdatedAt)`
- INDEX: `(userId,syncSeq)`
- INDEX: `(userId,boxId,deletedAt)`

BoxLocation:
- PRIMARY KEY / compound id: `(userId,id)`
- FK: `userId -> User.id ON DELETE CASCADE`
- INDEX: `(userId,serverUpdatedAt)`
- INDEX: `(userId,syncSeq)`
- INDEX: `(userId,name,deletedAt)`

`BoxLocation.name` はtombstoneを含む単純UNIQUEにしない。active name一意と後勝ちrenameはservice transactionで保証する。

SyncChangeLog:
- PRIMARY KEY: `syncSeq`
- FK: `userId -> User.id ON DELETE CASCADE`
- INDEX: `(userId,syncSeq)`
- INDEX: `serverUpdatedAt`（retention cleanup）

SyncConflict:
- PRIMARY KEY: `id`
- FK: `userId -> User.id ON DELETE CASCADE`
- UNIQUE: `(userId,entityType,entityId,clientBaseRevision,clientContentHash)`
- INDEX: `(userId,entityType,entityId)`

RestoreLock:
- PRIMARY KEY/FK: `userId -> User.id ON DELETE CASCADE`
- INDEX: `expiresAt`

RestoreApplyResult:
- PRIMARY KEY: `(userId,applyId)`
- FK: `userId -> User.id ON DELETE CASCADE`
- INDEX: `committedAt`（7日retention cleanup）

### 15.2 FK delete action
Business間FKにDB-level `ON DELETE CASCADE` を使用しない。

Box / Item / BoxLocationの通常削除はphysical deleteではなくtombstoneであり、child補正をservice transactionで実行する。

User自体の物理削除時だけUser FKの `ON DELETE CASCADE` によりUser scope全体を削除可能とする。

### 15.3 DB CHECK相当
SQLite/Prismaでportableに表現しにくいCHECKをPrisma schemaだけへ依存させない。以下はservice validation必須:
- Box.code canonical format
- reserved `UNASSIGNED` rule
- required display stringのtrim/NFC/empty rejection
- thumbs 0〜10
- photoHash format
- contentHash format
- revision/syncSeq range
- Box.code immutable

DB constraint violationは最後の防御であり、validation errorへmappingする。

## 16. Server transaction boundaries

### 16.1 Normal entity create/update
1 transaction:
1. authenticated User scope確定
2. current row取得
3. baseRevision/contentHash検証
4. business validation
5. 必要ならBoxLocation name collision解決
6. canonical contentHash算出
7. Business row insert/update + revision increment
8. serverUpdatedAt設定
9. global syncSeq採番
10. Business.syncSeq設定
11. SyncChangeLog insert
12. 必要ならSyncConflict削除
13. commit

### 16.2 Item delete
Item tombstone + metadata + SyncChangeLogを1 transaction。

### 16.3 Box delete
1 transaction:
1. Boxをlock対象としてcurrent revision確認
2. active child Itemsを取得
3. 各childを `boxId=UNASSIGNED` へ更新
4. 各child revision/contentHash/serverUpdatedAt/syncSeq更新 + SyncChangeLog
5. Box tombstone
6. Box metadata/syncSeq更新 + SyncChangeLog
7. commit

### 16.4 BoxLocation delete
Box deleteと同様にactive child Boxesを `locationId=UNASSIGNED` へ更新してからLocationをtombstone化し、全変更を1 transaction。

### 16.5 BoxLocation name collision
1 transaction:
1. requested normalized nameを確定
2. same Userの同名active recordを検索
3. 存在し別idなら既存record用の最小未使用 `name(n)` を決定
4. 既存recordをrenameしmetadata/syncSeq/SyncChangeLog更新
5. requested recordをcreate/update
6. requested record metadata/syncSeq/SyncChangeLog更新
7. commit

SQLiteのwriter serializationを利用するが、処理は必ず同一Prisma transaction内で行い、アプリ側の事前検索だけで一意性を保証しない。

### 16.6 SyncConflict resolution
current server revisionを再確認し、staleなら同じConflict rowのserver snapshotを更新する。解決を適用する場合はBusiness更新、metadata、syncSeq、SyncChangeLog、SyncConflict削除を1 transaction。

### 16.7 Restore apply
Restore lock ownershipとapplyId/requestDigestを検証した上で、Restore Business changes、各metadata/syncSeq、SyncChangeLog、`RestoreApplyResult(COMMITTED)` を1 server transactionでcommitする。

photo binary自体はtransaction前にserver-readyであることを検証する。

### 16.8 Batch Push
Push HTTP request全体を1 transactionにはしない。各logical operationを独立transactionとして処理し、entityごとの結果を返す。

## 17. syncSeq allocation
`syncSeq` はDB-wide signed 64-bit monotonic sequence。

SQLiteには独立sequence機能を前提とせず、専用1-row counterをserver DBに持つ。

```text
SyncSequence
id        "GLOBAL" PK
lastSeq   int64
```

Business transaction内でcounterをincrementし、必要な変更数だけ連続値を割り当てる。同一logical transaction内の複数Business変更にもそれぞれ別syncSeqを付与する。

番号の欠番は許容するが、重複と逆行は禁止する。

## 18. Physical cleanup
physical cleanupは通常Business transactionとは分離する。

- Business tombstone: server受理DELETEから30日後にphysical delete可能
- SyncChangeLog: 90日
- RestoreApplyResult: 7日
- unreferenced blob: 30日

cleanupはBusiness意味を変更してはならない。特にFK参照中のBusiness row/photo blobは削除不可。
