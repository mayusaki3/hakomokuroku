# 仕様・テスト仕様・実装再確認ロードマップ

## 1. 目的

本ロードマップは、箱目録の認証系 API について、以下の一方向確認を成立させるための作業計画を定義する。

```text
仕様
  ↓
テスト仕様
  ↓
実装 / テスト
```

目的は、現在の「テストが通る状態」を維持しつつ、HLDocS 対応に必要な以下を整備することである。

- 仕様と現行実装の差異を明示する
- テスト仕様と Vitest の対応関係を明示する
- sec_id 単位で検証責務を追跡できるようにする
- 仕様変更時に、テスト仕様と実装へ一方向に反映できる構造へ移行する
- 各段階でローカル環境の Vitest 実行結果を確認し、テスト成功状態を維持する

## 3. 現在確認済みの仕様不整合

## 3.1 `POST /api/auth/login`

### 不整合

API仕様では request body が以下の前提になっていた。

```json
{
  "email": "string",
  "password": "string"
}
```

一方、現行実装および現行 Vitest は以下を使用している。

```json
{
  "userId": "string",
  "password": "string"
}
```

### 判断

Phase 1 では現行実装・現行テストを正とし、仕様・テスト仕様を `userId/password` に合わせる。

---

## 3.2 `POST /api/auth/login/totp`

### 不整合

API仕様では、前段の `/api/auth/login` が `LoginChallenge` を発行し、`/api/auth/login/totp` は `challengeId` を受け取る前提である。

一方、テストケース仕様の一部には Cookie `sid` を前提とする記述が残っていた。

### 判断

現行仕様・現行実装は `challengeId` 前提で整合しているため、Cookie `sid` 前提の記述を廃止する。

## 4.2 作業順

### P1-1. 仕様差異表の作成

各 API について以下を表で整理する。

| 項目 | 仕様 | テスト仕様 | 実装 | Vitest | 判定 |
|------|------|------------|------|--------|------|
| Request body |  |  |  |  |  |
| Response body |  |  |  |  |  |
| Status code |  |  |  |  |  |
| Cookie / Header |  |  |  |  |  |
| DB 更新 |  |  |  |  |  |

### P1-2. 正本方針の確定

以下を API ごとに確定する。

- 現行実装を正として仕様を修正するか
- 仕様を正として実装を修正するか
- 実装差異許容を残すか、削除するか

### P1-3. API仕様修正

HLDocS 対応を見据えて、API仕様を以下の粒度へ分割する。

- sec_id 単位で検証責務を定義する
- request / response / status / side effect を分離する
- 実装差異許容を最小化する

### P1-4. テストケース仕様修正

テストケース仕様を以下の形式へ寄せる。

- 1 テストケース = 1 主検証責務
- 各テストケースに対象 sec_id を明記する
- 実装依存の許容範囲を削減する
- 現行 Vitest 名と対応できる ID を維持する

### P1-5. Vitest 確認

仕様・テストケース仕様の修正後、ローカル環境で以下を実行する。

```bash
pnpm -C apps/web exec vitest --run --coverage --config vitest.config.mts --reporter=verbose
```

確認結果はチャットへ貼り付け、失敗があれば次の作業前に原因を切り分ける。

- totp/recovery/reissue

### 5.1 Phase 2 の作業単位

各 API について、以下の順で進める。

1. API仕様へ sec_id を追加する
2. テストケース仕様へ TC ↔ sec_id 対応表を追加する
3. route.ts へ sec_id コメントを追加する
4. Vitest の `it(...)` 名と TC ID の対応を確認する
5. ローカル環境で Vitest を実行し、成功/失敗を確認する

### 5.2 ローカル確認ルール

各 API 群の更新後、ユーザーのローカル環境で以下を実行する。

```bash
pnpm -C apps/web exec vitest --run --coverage --config vitest.config.mts --reporter=verbose
```

実行結果は以下の観点で確認する。

- Test Files が全件 passed であること
- Tests が全件 passed であること
- 今回更新対象外のテスト失敗が発生していないこと
- Coverage が大きく低下していないこと

失敗した場合は、次 API へ進まず、以下を先に実施する。

1. Failed Suites / Failed Tests の先頭スタックトレース確認
2. 仕様変更による期待値不一致か、実装コメント追加による副作用かを判定
3. テストまたは実装のどちらを修正すべきかを明示
4. 修正後に再度ローカル Vitest を実行

## 6. Phase 3: 実装構造整理

仕様とテスト仕様が正規化された後、以下を検討する。

```text
route.ts
  ↓
service
  ↓
repository
```

目的は、route test に集中している責務を分離し、以下を可能にすることである。

- service 単体テスト
- repository mock の共通化
- Prisma API 変更の影響範囲縮小
- API仕様と domain logic の対応明確化

Phase 3 の実装変更後も、必ずローカル Vitest を実行して確認する。

---

## 7. Phase 4: HLDocS 完全対応

以下を順に実施する。

1. 既存 API仕様へ LLM-MANAGED ブロックを導入
2. sec_id を検証責務単位で付与
3. テストケース仕様へ spec 参照を付与
4. Vitest テスト名またはコメントへ testspec 参照を付与
5. 実装コメントまたはドキュメント側へ code 参照を付与
6. ローカル Vitest 成功結果を確認する

最終目標は以下である。

```text
spec sec_id
  ↓
testspec TC
  ↓
Vitest it(...)
  ↓
route/service implementation
  ↓
local Vitest PASS
```
