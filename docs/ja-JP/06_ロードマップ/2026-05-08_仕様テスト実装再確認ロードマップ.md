# 仕様・テスト仕様・実装再確認ロードマップ

## 1. 目的

本ロードマップは、箱目録の認証系 API について、以下の一方向確認を成立させるための作業計画を定義する。

```text
仕様
  ↓
テスト仕様
  ↓
実装 / テスト
```

目的は、現在の「テストが通る状態」を維持しつつ、HLDocS 対応に必要な以下を整備することである。

- 仕様と現行実装の差異を明示する
- テスト仕様と Vitest の対応関係を明示する
- sec_id 単位で検証責務を追跡できるようにする
- 仕様変更時に、テスト仕様と実装へ一方向に反映できる構造へ移行する

## 3. 現在確認済みの仕様不整合

## 3.1 `POST /api/auth/login`

### 不整合

API仕様では request body が以下の前提になっている。

```json
{
  "email": "string",
  "password": "string"
}
```

一方、現行実装および現行 Vitest は以下を使用している。

```json
{
  "userId": "string",
  "password": "string"
}
```

### 判断が必要な点

以下のどちらを正とするかを決める必要がある。

| 案 | 正とする入力 | 影響 |
|----|--------------|------|
| A | `userId/password` | 現行実装・テストを維持し、仕様・テスト仕様を修正する |
| B | `email/password` | 仕様を維持し、実装・テストを修正する |

### 暫定方針

現行テストが全件成功しており、実装も `userId/password` で安定しているため、Phase 1 では案 A を優先する。

---

## 3.2 `POST /api/auth/login/totp`

### 不整合

API仕様では、前段の `/api/auth/login` が `LoginChallenge` を発行し、`/api/auth/login/totp` は `challengeId` を受け取る前提である。

一方、テストケース仕様の一部には Cookie `sid` を前提とする記述が残っている。

### 判断

現行仕様・現行実装は `challengeId` 前提で整合しているため、Cookie `sid` 前提の記述を廃止する。

### 暫定方針

`login/totp` は以下を正とする。

```json
{
  "challengeId": "string",
  "code": "string",
  "recoveryCode": "string"
}
```

- Cookie 認証は不要
- `challengeId` は `/api/auth/login` で発行された LoginChallenge.id
- 認証成功時のみ token / cookie を発行する

## 4. Phase 1: API仕様正規化

## 4.2 作業順

### P1-1. 仕様差異表の作成

各 API について以下を表で整理する。

| 項目 | 仕様 | テスト仕様 | 実装 | Vitest | 判定 |
|------|------|------------|------|--------|------|
| Request body |  |  |  |  |  |
| Response body |  |  |  |  |  |
| Status code |  |  |  |  |  |
| Cookie / Header |  |  |  |  |  |
| DB 更新 |  |  |  |  |  |

### P1-2. 正本方針の確定

以下を API ごとに確定する。

- 現行実装を正として仕様を修正するか
- 仕様を正として実装を修正するか
- 実装差異許容を残すか、削除するか

### P1-3. API仕様修正

HLDocS 対応を見据えて、API仕様を以下の粒度へ分割する。

- sec_id 単位で検証責務を定義する
- request / response / status / side effect を分離する
- 実装差異許容を最小化する

### P1-4. テストケース仕様修正

テストケース仕様を以下の形式へ寄せる。

- 1 テストケース = 1 主検証責務
- 各テストケースに対象 sec_id を明記する
- 実装依存の許容範囲を削減する
- 現行 Vitest 名と対応できる ID を維持する

### P1-5. Vitest 確認

仕様・テストケース仕様の修正後、以下を実行する。

```bash
pnpm -C apps/web exec vitest --run --coverage --config vitest.config.mts --reporter=verbose
```

## 6. Phase 3: 実装構造整理

仕様とテスト仕様が正規化された後、以下を検討する。

```text
route.ts
  ↓
service
  ↓
repository
```

目的は、route test に集中している責務を分離し、以下を可能にすることである。

- service 単体テスト
- repository mock の共通化
- Prisma API 変更の影響範囲縮小
- API仕様と domain logic の対応明確化

---

## 7. Phase 4: HLDocS 完全対応

以下を順に実施する。

1. 既存 API仕様へ LLM-MANAGED ブロックを導入
2. sec_id を検証責務単位で付与
3. テストケース仕様へ spec 参照を付与
4. Vitest テスト名またはコメントへ testspec 参照を付与
5. 実装コメントまたはドキュメント側へ code 参照を付与

最終目標は以下である。

```text
spec sec_id
  ↓
testspec TC
  ↓
Vitest it(...)
  ↓
route/service implementation
```
